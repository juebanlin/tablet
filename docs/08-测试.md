# 测试

## 1. 测试架构

测试体系以 shell 脚本为主体，通过调用 `tablet-cli` 二进制验证所有 CLI 命令的正确性。辅以 Python 脚本生成大量随机测试数据用于性能测试。

### 1.1 设计原则

- **shell 为主体**：CLI 是 shell 工具，测试也用 shell 驱动
- **临时目录隔离**：每个测试用 `mktemp -d` 创建独立 workspace，测试完自动清理（trap EXIT）
- **无残留**：测试不在 tests/ 目录下产生任何持久文件
- **Python 仅做数据工厂**：被 shell 调用生成大量 .tbl 数据行

### 1.2 核心流程

```
tests/run_all.sh
    ├── 遍历 01_project/ ~ 11_e2e/ 下所有 test_*.sh
    ├── 每个 test_*.sh:
    │   ├── source helpers/common.sh
    │   ├── setup_workspace（创建临时 workdir + 项目）
    │   ├── run_cli ... → 断言 exit code / stdout / stderr / 文件存在
    │   └── cleanup（自动，trap EXIT）
    └── 汇总 PASS / FAIL
```

### 1.3 内置 Schema 文件

位于 `crates/core/schemas/`，测试用副本在 `tests/schemas/`：

| 文件 | 用途 |
|------|------|
| `standard.tblschema` | 通用测试（所有基础类型 + 集合 + 元组 + 引用 + 常量 + 枚举） |
| `sanguo.tblschema` | 大数据量性能测试（100+ 行预设，8 枚举，6 表） |
| `minimal.tblschema` | 最小测试（单 group + 单 table，快速验证） |

**为什么 e2e 必须存在**：只断言生成器吐出的字符串，漏得掉「产物本身跑不通」。现实教训——C# 的 `Loader` 曾因为 C# 静态构造器是惰性的而**静默一张表都不加载**（`Get(id)` 全返回 `null`），而所有字符串级断言都是绿的。详见 @11.3.3。缺工具链的用例会 SKIP 并打印提示，不会假装通过。

> **工具发现别用裸 `command -v`**：测试跑在 **Git Bash**（Git for Windows 自带的 bash，非完整 MSYS2）下，它和 cmd 的行为不一样，有两个坑，`find_tool`（见 `helpers/common.sh`）一并处理了：
> 1. **同名目录会挡住同名 `.exe`**——cmd 按 PATHEXT 搜 PATH 且跳过目录，所以 cmd 下 `lua` 正常；Git Bash 沿 PATH 撞到叫 `lua` 的**目录**就不再找 `lua.exe` 了。LuaRocks 的 `C:\Program Files (x86)\Lua\5.1\lua` 正是这个目录。
> 2. **装了但没进 PATH**——Lua 与 npm 全局的 `tsc` 默认都不在 PATH 上。
>
> 所以候选名一律连 `<name>.exe` 一起试，并允许传额外搜索目录兜底。装了却仍报 SKIP 时用环境变量指路：`LUA_BIN=... TSC=... ./tests/run_all.sh`。
>
> **`lombok.jar` 单独一个机制**：它不在 PATH 上，`find_lombok_jar` 按 `LOMBOK_JAR` 覆盖 → **问 maven 本地仓库在哪** → 解析 `settings.xml` 兜底 → 默认 `~/.m2/repository` → gradle 缓存的顺序找，取版本号最高的那个。
>
> **本地仓库位置走 maven 上层接口而不是自己猜**：它由 `settings.xml` 的 `<localRepository>`（用户级 / 全局）、`-Dmaven.repo.local` 多层配置决定，`~/.m2/repository` 只是默认值。`maven_local_repository()` 直接跑 `mvn help:evaluate -Dexpression=settings.localRepository -DforceStdout` 让 maven 自己算完再回答。代价是 trampoline 一个 JVM（本机实测冷启 ~7.5s、暖缓存 ~1.5s），所以 maven 够不着时（不在 PATH、也没设 `MVN` / `MAVEN_HOME` / `M2_HOME`）才回落去解析 `settings.xml`。
>
> **Windows 路径必须转 MSYS 形式**（`D:\a` → `/d/a`，`to_msys_path()`）：`D:/...` 塞进 `-cp "src:D:/jar"` 这种**冒号分隔**的列表里会被 MSYS 拆错，jar 悄悄没进 classpath，症状是「程序包 lombok 不存在」。
>
> **Lombok 与 JDK 严格绑定**：它直接摸 javac 内部 API，jar 比 JDK 旧会崩在处理器初始化。判定不靠匹配编译错误文本（Lombok 的 deprecation 警告里也含 `lombok.permit.Permit`，会把真错误误判成版本不匹配而吞掉），而是 `lombok_usable()` **真编译一个探针类**，并用 `javap` 确认 Lombok 确实生成了 getter——顺带把「只给 `-cp` 时 javac 静默忽略注解处理器、exit 0 但产物没有 getter」也探掉了。不可用就 SKIP 并给出升级命令；真的编译失败照旧硬失败。升级：`mvn dependency:get -Dartifact=org.projectlombok:lombok:1.18.48`。

## 3. 运行方式

```bash
# 前置：编译 CLI（dev profile，@CLAUDE.md：日常不用 release）
cargo build -p tablet-cli

# 运行全部测试
bash tests/run_all.sh

# 跳过性能测试（CI 快速模式）
bash tests/run_all.sh --skip-perf

# 运行指定目录
bash tests/run_all.sh 01_project

# 运行单个测试文件
bash tests/01_project/test_new.sh
```

`run_all.sh` 默认走 **dev profile**（`target/debug/tablet-cli`），没编译会自动编。
`10_performance` 的耗时数字只在 release 下有意义，所以 CLI 不是 release 构建时该目录**自动跳过**并打印提示；要跑性能就显式指一个 release 产物：

```bash
cargo build -p tablet-cli --release
CLI=$PWD/target/release/tablet-cli bash tests/run_all.sh
```

## 5. 性能测试

使用多档位阶梯方式，测试不同数据规模下的耗时：

| 档位 | 行数 | 用途 |
|------|------|------|
| 小 | 100 | 基线 |
| 中 | 1,000 | 日常规模 |
| 大 | 10,000 | 中型项目 |
| 超大 | 100,000 | 压力边界 |

性能测试流程：
1. 用 `util scaffold` 从 sanguo.tblschema 生成骨架
2. 用 `helpers/datagen.py` 按字段类型生成 N 行随机数据
3. 运行 CLI 命令并计时
4. 输出耗时表格

```bash
=== JSON Export Performance ===
Rows       Time(s)
100        0.05
1000       0.12
10000      0.89
100000     8.34
```

### 6.1 Rust 单测（shell 够不到的地方）

shell 测试通过 CLI 驱动，所以**只能测 CLI 暴露的东西**。GUI 独占的能力没有 CLI 入口，只能落在 Rust 单测里（`cargo test --workspace`）：

- **`tablet_core::excel_sync`**（@06 §7 的同步引擎，仅同步面板调用）——31 条单测，按模块分三层：
  - `plan`（13 条）：**纯函数，不碰文件系统**。喂两个 `SheetVo` + 一个 schema，断言每行的 `ops`——完全匹配 / tablet 多列 / 两侧多列 / xlsx 多列 / 只有一侧 / 表头改坏 / 只改 desc / 旧布局 / type 越权 / 列映射落点。这几个场景以前只存在于文档表格里，靠 Rust 分支和 Slint 谓词手工对齐。
  - `read`（5 条）：无损投影。中间有空行时行号不丢、区域外内容不进 VO 但留在 `range`、desc 行存在但全空与「没有 desc 行」是两回事。
  - `apply`（13 条）：落盘与保真。`lazy_read` 字节直通、样式与自建 sheet 存活、**umya 往返的样式保真**（框架契约）、**初次生成不带任何样式**、`补列→` 是插入且**策划的公式列活下来**、`WholeTable` 就地清理、旧布局升级、回读「空 = 清空」、计划过期被拒、`←导入` 如实报未实现。
- `apply::tests::untouched_sheet_is_copied_byte_for_byte` 是唯一能**真正区分** `lazy_read` 与全量 `read` 的断言：它直接比对 xlsx（zip）里那张没被同步的 sheet 的**原始字节**。其余保真用例在全量 `read` 下也会通过，钉不住东西。
- `apply::tests::umya_round_trip_keeps_all_cell_styles` 是**框架契约**：不经过我们的代码，纯测 umya 的读→写往返。3.0.1 会丢边框、3.1.1 已修；这条把版本下限钉住（对应 `Cargo.toml` 的 `umya-spreadsheet = "3.1"`）。
- `apply::tests::apply_never_does_column_matching` 是**源码级**断言：读自己的源文件，确认 `apply.rs` 里不出现 `compute_column_match` / `classify_header`。列对齐只该发生在 `plan` 这个黑盒里。

> **写这类断言务必先用「把实现改坏」验证它会红。** 上面那两条红线都实测过：换成全量 `read`、往 `apply.rs` 塞一个 `compute_column_match` 调用，它们各自立刻失败。第一版写的保真用例就是这样被抓出来的假绿——它在全量 `read` 下也照样通过。

该用例依赖 `zip`（dev-dependency，只测试用），并且被保留的 sheet 必须由 **umya 之外**的库写出：umya 重新序列化自己的输出是幂等的、字节不变，拿它造的 sheet 去测「有没有被重写」永远测不出来。
