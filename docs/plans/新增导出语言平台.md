# Plan: 新增导出语言平台（客户端 4 + 服务端 1） + 类型/枚举范式兼容

> 计划文档（pre-implementation 备忘）。实施完成后此文件可删除或归档；正式章节内容会同步进 `docs/02-核心功能.md` / `docs/03-CLI工程.md`。

## Context

当前 tablet 已实现 5 个导出目标（`crates/core/src/export/{json,xml,java,go,lua}.rs`）。本次新增 5 个语言平台，覆盖客户端 4 个（Unity C# / Godot C# / GDScript / TypeScript）+ 服务端 1 个（C++），并明确 Kotlin 的处置方式。

实现这批新导出器**最关键的不是写 Loader 模板**，而是让它们对齐 Java/Go/Lua 已经做到的「类型系统 + 枚举 + 跨引用 + Constant」四件事——这是 java/go/lua 跑了一年后稳定下来的范式，新导出器一旦没对齐就会在用户的真实数据上炸。

## 1. 全部支持平台一览

> 标 ✅ 是已实现，✨ 是本次新增，🟡 是「映射到现有导出器，无需新建」

## 2. 核心问题决策

### 2.1 Kotlin：直接复用 java.rs，不新建

Kotlin 在 JVM 上 100% 互操作 Java——`val hero: HeroBaseTpl = TplHolder.getHero(1)` 直接读 .class 字节码、命中 java.rs 生成的 getter 完全无感。Spring Boot / Ktor 的 Kotlin 项目实际就是把 Java 配置工程当依赖引入。

**结论**：不新建 kotlin.rs，文档里加一条「Kotlin 服务端复用 `--java` 输出」即可，零工作量。

代价：生成的类是 Java 风格 getter（`getHp()`），不是 Kotlin 的 `val hp` 属性语法——但 Kotlin 本身把 Java getter 自动暴露成 `tpl.hp` 属性访问，用户层无感。如果未来真有强诉求要原生 Kotlin data class，再单建。

### 2.2 C++ 服务端：必须新建（Java 不能复用）

C++ 没法吃 .java，且 Unreal C++ / 自研引擎 C++ 服务端是真实需求。新建 `cpp.rs`，分离模式：生成 `.h` schema 头 + `.cpp` Loader + 复用 JSON 数据。考虑：

- 用 `std::vector` / `std::unordered_map` 做容器（标准库不引第三方 STL 替代）
- 枚举用 `enum class HeroTypeEnum : int32_t { ... }`（带强类型）
- JSON 解析推荐 `nlohmann/json`（header-only，社区主流），Loader 模板里给个开关字符串切 RapidJSON
- 头文件守护用 `#pragma once`（现代编译器全支持）

### 2.3 csharp 单导出器 + runtime 子参数

参考前一版 plan 的判断：Unity / Godot / .NET 三个 runtime 共享 schema 类（HeroBase.cs 字段定义）和 JSON 数据，只在 `Loader.cs` 模板上分三套：

| runtime | 加载入口 | JSON 库 |
|---------|---------|--------|
| `unity` | `Resources.Load<TextAsset>("data/HeroBase").text` | Newtonsoft.Json（Unity 几乎都装了）或 JsonUtility |
| `godot` | `FileAccess.open("res://data/HeroBase.json", READ).get_as_text()` | Godot 自带 `Json` 类 |
| `dotnet` | `File.ReadAllText("data/HeroBase.json")` | `System.Text.Json` |

### 2.3 csharp 拆三个独立配置 key（不用 runtime 字段）

C# 三个目标平台（.NET / Unity / Godot）的差异**只在 Loader.cs 一个文件**——schema 类（占 95% 代码量）完全共享。原本设想用 `runtime` 字段切，但有硬伤：**一个项目可能同时需要 Unity + Godot 双客户端**（主端 Unity + 工具/Web 端 Godot），runtime 单字段方案只能选一个。

**方案**：拆成三个独立 toml key，配置自解释，无需 runtime 字段、无需白名单校验。

| toml key | side | Loader 模板 | 默认 JSON 库 |
|---------|------|-----------|------------|
| `csharp_dotnet` | server | `File.ReadAllText("data/X.json")` | `System.Text.Json` |
| `csharp_unity` | client | `Resources.Load<TextAsset>("data/X").text` | `Newtonsoft.Json`（Unity 包默认装） |
| `csharp_godot` | client | `FileAccess.open("res://data/X.json", READ).get_as_text()` | `System.Text.Json` 或 Godot 自带 `Json` |

`tablet.toml` 配置：

```toml
# 顶层（已有）：data 输出路径在这里定，所有 server/client 端语言共享
[export.server]
data_output = "gen/server/data"

[export.client]
data_output = "gen/client/data"

# C# 三平台拆三个 key
[export.server.csharp_dotnet]
namespace   = "Game.Config.Server"
code_output = "gen/server/csharp"

[export.client.csharp_unity]
namespace   = "Game.Config.Client.Unity"
code_output = "gen/client/csharp_unity"

[export.client.csharp_godot]
namespace   = "Game.Config.Client.Godot"
code_output = "gen/client/csharp_godot"

[export.client.gdscript]
output      = "gen/client/gdscript"

[export.client.typescript]
output      = "gen/client/typescript"
module_kind = "esm"

[export.server.cpp]
namespace   = "game::config"
code_output = "gen/server/cpp"
json_lib    = "nlohmann"        # "nlohmann" | "rapidjson"
```

**显式禁用语言级 data 路径覆盖**（决策记录，便于后续抵御新增需求）：

- 不在 `[export.{side}.{lang}]` 提供 `data_output` 字段；如果用户配了应解析报错或忽略+警告
- 数据输出维度严格 = side 维度（server / client），不掺语言维度
- 同 side 多语言（java + go + csharp_dotnet / csharp_unity + csharp_godot）共读同一份 data
- 反例「希望直接写到 Unity Assets/Resources/data」走项目构建脚本 `cp` 解决，不是导出工具的责任
- 如果未来真的有强诉求，应该走顶层 `[export.client] extra_copy_to = [...]` 镜像复制（不是语言级覆盖），但**本次不实现**

### 2.3.1 csharp 三 key 的实现 / CLI / UI 一致性

#### 实现层共享

core 内部仍是**单一** `crates/core/src/export/csharp.rs`，不拆三个文件。generator 函数接 `enum CSharpRuntime { Dotnet, Unity, Godot }` 参数，按值切 Loader 模板，schema 类生成代码 100% 共享。

`ops.rs` 暴露三个入口（按 toml 配置三个 key 一一对应）：

```rust
ProjectEngine::export_csharp_dotnet()    // → csharp::generate(project, CSharpRuntime::Dotnet, Side::Server)
ProjectEngine::export_csharp_unity()     // → csharp::generate(project, CSharpRuntime::Unity,  Side::Client)
ProjectEngine::export_csharp_godot()     // → csharp::generate(project, CSharpRuntime::Godot,  Side::Client)
```

#### CLI flag

保持单 `--csharp` flag，跟 `--java` `--go` 同范式：

- `tablet-cli export --csharp` → 跑配置里所有 `csharp_*` key
- 要细控就注释 toml 不想跑的 key
- MVP 不引入 `--csharp-unity` / `--csharp-godot` / `--csharp-dotnet` 拆分；未来按需

#### UI 标签

「导出设置」对话框按 **服务端 / 客户端** 分组，C# 三 key 的标签直接按后缀映射：

| toml key | UI 显示 |
|---------|--------|
| `csharp_dotnet` | 服务端组：**C# (.NET)** |
| `csharp_unity` | 客户端组：**C# (Unity)** |
| `csharp_godot` | 客户端组：**C# (Godot)** |

UI 不显示 toml 路径串。同 side 下用户勾选哪些就生成哪些；同时勾 unity 和 godot 出两份。

#### 物理隔离三层

1. **路径**：`code_output` 默认 `gen/server/csharp/` / `gen/client/csharp_unity/` / `gen/client/csharp_godot/`
2. **namespace**：`Game.Config.Server` vs `Game.Config.Client.Unity` vs `Game.Config.Client.Godot`
3. **类名**：保持一致（三份都叫 `HeroBaseTpl`），靠 namespace 区分

不加 side / runtime 前缀到类名的理由：多数项目要么单端、要么单 runtime，前缀让代码变丑；极少数同 solution 引用多端的场景让用户用 `using` alias 解决。

#### 错配防御不再需要

之前 runtime 方案需要白名单校验「server 不能配 unity / client 不能配 dotnet」，拆 key 后**自然消失**——错配 toml 比如 `[export.server.csharp_unity]`，解析阶段因为「server 没有 csharp_unity 注册」直接报「未知 export 类型」，错误源头从「runtime 字段填错」变成「key 写错」，后者比前者更显眼。

### 2.4 数据文件复用 json 输出

csharp / cpp 不重新生成数据，仅生成代码——数据由现有 `--json` 顺带产出。CLI 层让 `--csharp` / `--cpp` 隐式触发 `--json`（参考 java.rs 当前行为）。

### 2.5 数据目录布局：保持 `gen/{server,client}/data/`

**关键澄清**：server 端和 client 端**应该且必须**生成两份独立的数据文件，因为它们的字段集合根本不同：

- `gen/server/data/json/HeroBase.json` 含 `cs + s` 字段（带服务器机密：`loot_table_internal` / `server_only_param` 等）
- `gen/client/data/json/HeroBase.json` 含 `cs + c` 字段（不含服务器机密；客户端 .apk/.ipa 反编译能拿到所有字段，机密不能进这里）

**服务端多语言 / 客户端多语言时数据文件复用**：

| 场景 | 数据文件产出 |
|------|-----------|
| server: java + go（双后端） | 仅 `gen/server/data/json/`，java 和 go 共读这一份 |
| server: java + cpp + csharp(.NET) | 仅 `gen/server/data/json/`，三个 Loader 共读 |
| client: csharp(unity) + csharp(godot)（同游戏多端） | 仅 `gen/client/data/json/`，两个 Loader 共读 |
| **server: java，client: csharp(unity)** | **server/data 和 client/data 两份，字段集不同——必须** |
| server: java，client: lua/gdscript/typescript | 仅 `gen/server/data/json/`（client 端内嵌模式无独立数据文件） |

**目录结构定型**（实施时严格按这个走）：

```
gen/
  server/
    data/
      json/         ← 仅 cs+s 字段
      xml/
    java/           ← *.java schema 类
    go/
    csharp/         ← *.cs schema 类 + Loader（runtime=dotnet）
    cpp/            ← *.h/*.cpp schema + Loader
  client/
    data/
      json/         ← 仅 cs+c 字段，不含服务器机密
      xml/
    csharp/         ← runtime=unity 或 godot
    gdscript/       ← 内嵌，无 data
    typescript/     ← 内嵌，无 data
    lua/            ← 内嵌，无 data
```

**为什么不抽 `gen/data/{server,client}/`**：Jenkins 打服务器包只拷 `gen/server/`、打客户端包只拷 `gen/client/`，单路径自包含；提到顶层 data/ 后打包脚本要拷两个路径，无谓复杂化。

**为什么不抽 shared/ 三份去重**：Loader 要从两个文件 merge 数据，代码复杂度上升、增量热更复杂、json 体积省下来的 KB 不值得。

## 3. 类型/枚举/范式兼容性 checklist（关键）

每个新导出器必须在 PR 提交前确认全部通过。源头：调研到的 java/go/lua 都已对齐这些点。

### 3.1 BaseType（6 种）

每种的语言映射必须显式列：

| BaseType | C# | C++ | GDScript | TypeScript |
|---------|----|----|---------|----------|
| Int | `int` | `int32_t` | `int` | `number` |
| Long | `long` | `int64_t` | `int`（GDScript int 是 64-bit） | `bigint` 或 `number`（< 2^53 时安全） |
| Float | `float` | `float` | `float`（GDScript 是 64-bit） | `number` |
| Double | `double` | `double` | `float` | `number` |
| Str | `string` | `std::string` | `String` | `string` |
| Bool | `bool` | `bool` | `bool` | `boolean` |

> TypeScript Long 决策：默认 `number`（JS 引擎下 Number.MAX_SAFE_INTEGER = 2^53-1，业务里 id/timestamp 一般够），如果 schema 里出现 long 字段且数值超出安全范围才警告——但本次先不做溢出检测，配文档说明即可。

### 3.2 Paradigm（共 15 种）容器映射

源码 `crates/core/src/types.rs:153-170` 定义 Paradigm 共 **15 种**：

```
Base                          ← 裸 BaseType 字段
Tuple2 / Tuple3 / Tuple4
List / Set / Map
ListTuple2 / ListTuple3 / ListTuple4
MapTuple2 / MapTuple3 / MapTuple4
MapList
Ref                           ← @TableName / @EnumName，存为 int(id)
```

分类：
- `Paradigm::all()` = 15 种（全集）
- `Paradigm::all_data()` = 14 种（不含 Ref，UI 类型选择器用）
- 「真·容器范式」= 13 种（去掉 Base 和 Ref）
- **25 项分隔符 leaf** 来自 `SeparatorsSection`（不等于 Paradigm 数量）：每个容器 paradigm 需要 1-3 个分隔符（Tuple 一个、Map 两个、嵌套类两个），合计 25 个 leaf

每个新导出器必须从 `SeparatorsSection` 读取分隔符，**不能硬编码**。

每种 Paradigm 在 4 种新语言下的具体化映射：

| Paradigm | C# | C++ | GDScript | TypeScript |
|---------|----|----|---------|----------|
| Base | `int` / `string` / ... | `int32_t` / `std::string` / ... | `int` / `String` / ... | `number` / `string` / ... |
| Tuple2<A,B> | `(A, B)` 值元组 | `std::tuple<A,B>` | `Array`（无 tuple，按 [A,B] 处理） | `[A, B]` |
| Tuple3 / Tuple4 | `(A,B,C)` / `(A,B,C,D)` | `std::tuple<...>` | `Array` | `[A,B,C]` / `[A,B,C,D]` |
| List<T> | `List<T>` | `std::vector<T>` | `Array[T]`（typed array） | `T[]` |
| Set<T> | `HashSet<T>` | `std::unordered_set<T>` | `Array[T]`（GDScript 无 Set） | `Set<T>` |
| Map<K,V> | `Dictionary<K,V>` | `std::unordered_map<K,V>` | `Dictionary` | `Map<K,V>` 或 `Record<K,V>` |
| ListTuple2<A,B> | `List<(A,B)>` | `std::vector<std::tuple<A,B>>` | `Array[Array]` | `Array<[A,B]>` |
| ListTuple3 / ListTuple4 | `List<(A,B,C)>` / `List<(A,B,C,D)>` | `std::vector<std::tuple<...>>` | `Array[Array]` | `Array<[A,B,C]>` / `Array<[A,B,C,D]>` |
| MapTuple2<K,A,B> | `Dictionary<K, (A,B)>` | `std::unordered_map<K, std::tuple<A,B>>` | `Dictionary` | `Map<K, [A,B]>` |
| MapTuple3 / MapTuple4 | `Dictionary<K, (A,B,C)>` / 4 元 | `std::unordered_map<K, std::tuple<...>>` | `Dictionary` | `Map<K, [A,B,C]>` / 4 元 |
| MapList<K,V> | `Dictionary<K, List<V>>` | `std::unordered_map<K, std::vector<V>>` | `Dictionary` | `Map<K, V[]>` |
| Ref（@HeroBase） | 字段类型为 `int`（保留 id），编译型语言可选生成 `HeroBase Get()` helper | 同 C# | 同 Lua，保留 int | 同 Lua，保留 int |
| Ref（@HeroType / 枚举） | `HeroTypeEnum` | `HeroTypeEnum` | `int` | `HeroType`（TS 枚举） |

GDScript / TypeScript 由于「内嵌模式」实际不需要 Loader 解析，直接 const literal 输出（`{"key": [1,2,3]}` / `[[1,2],[3,4]]`），但**类型注解仍需对应**——GDScript 4.0+ 支持 typed array，TypeScript 永远要类型。

### 3.3 枚举字段引用（@HeroType）

字段类型写 `@EnumName` 时：

| 导出器 | 行为 |
|-------|------|
| Java/Go/C#/C++ | 字段类型改为 `HeroTypeEnum`，值通过 `fromId(int)` / `(HeroTypeEnum)id` / `static_cast` 转换 |
| Lua/GDScript/TypeScript | 字段类型保留为 `int`（脚本语言枚举即 int 常量，字典查询性能更好） |

### 3.4 EnumDef 导出形态

| 语言 | 形态 |
|------|------|
| C# | `public enum HeroTypeEnum : int { Warrior = 1, Mage = 2 }` + `static class HeroTypeEnumExt { static string GetDesc(this HeroTypeEnum) }` |
| C++ | `enum class HeroTypeEnum : int32_t { Warrior = 1, Mage = 2 };` + `inline const char* getDesc(HeroTypeEnum)` |
| GDScript | `const HeroType = { Warrior = 1, Mage = 2, _desc = { 1: "战士", 2: "法师" } }`（const dict，跟 Lua 同形） |
| TypeScript | `export enum HeroType { Warrior = 1, Mage = 2 }` + `export const HeroTypeDesc: Record<HeroType, string> = {...}` |

### 3.5 Constant 段导出形态

| 语言 | 形态 |
|------|------|
| C# | `public static class GlobalConstTpl { public const int MaxLevel = 100; }` |
| C++ | `namespace global_const { constexpr int max_level = 100; }`（或 `inline constexpr` 视 C++17+） |
| GDScript | `const GlobalConst = { max_level = 100 }`（const dict） |
| TypeScript | `export const GlobalConst = { max_level: 100 } as const;`（用 `as const` 让 IDE 推出字面量类型） |

### 3.6 RefIndex（跨表引用）

跟 java/go/lua 一致：导出器不用 RefIndex，schema 验证层（`validate.rs`）已经保证数据合法。引用字段在导出层就当 int 处理。

### 3.7 分隔符元数据

GDScript / TypeScript 走内嵌模式，**完全不需要分隔符**（数据已经被工具切分好直接写成数组/字典字面量）。csharp / cpp 走分离模式，需要 Loader 在运行时按 SeparatorsSection 切分——所以生成代码时要把分隔符值嵌进 Loader（或单独写一份 separators.json/.cs/.h），具体化方式：

- C#：`Loader.cs` 顶部生成 `private const char SEP_LIST = '|';` 等常量（从 SeparatorsSection 取）
- C++：`loader.h` 顶部生成 `constexpr char SEP_LIST = '|';`

参考 java.rs 现有做法，照搬。

## 5. 风险与边界

1. **C++ JSON 库依赖**：`nlohmann/json` 是 header-only 库（用户复制头文件即用），不强制项目用 vcpkg/conan。但仍要在生成 .h 顶部加 `#include <nlohmann/json.hpp>` —— 用户负责自己引入。
2. **Unity IL2CPP 反射保留**：`Newtonsoft.Json` 在 IL2CPP 上需要 `link.xml` 保留类型，否则被剥离。Loader 模板里加注释提示，**不在工具里管 link.xml**（属于 Unity 项目工程问题）。
3. **GDScript const dict 体积**：超大表（>5MB）解析慢。本次不做分片，遇到再优化。
4. **TypeScript Long 溢出**：默认 `number`，超过 2^53 不报错只警告（甚至先不警告）。文档里说明限制。
5. **Kotlin 路径**：仅文档里说明「复用 --java 输出」，不引入 `--kotlin` flag——避免给用户错觉以为有原生 Kotlin data class 输出。
6. **csharp 三 runtime 模板维护成本**：Loader 三份模板用 Rust 多行字符串 + 简单变量替换即可，不引模板引擎。每次修 schema 类生成逻辑只改一处，三份 Loader 各自独立维护。

   **为什么不合并成单一 csharp 输出**（决策记录）：曾考虑把 Loader 改成 IO 可注入形态（`Loader.LoadAll(Func<string,string> readJson)`），让用户在 Unity / Godot / .NET 各自写 1 行 bootstrap 共用同一份产物。否决理由：
   - **方向不可逆**：合 → 拆比拆 → 合代价大得多。今天 Unity 和 Godot 的 Loader 差异只有 IO 一行，但未来 Godot 4.x 引入新 Resource API、Unity 转 Addressables、或某 runtime 想用专属 JSON 库（Unity 上 Newtonsoft vs .NET 上 System.Text.Json 在 Tuple 反序列化行为已经不同），合并方案就崩了
   - **三 key 现在不阻塞「只用 Unity」**：用户配 `[export.client.csharp_unity]` 就只跑 unity，不会强迫连带 godot
   - **开箱即用**：拆开后每个 runtime 的 Loader 直接调原生 API（`Resources.Load` / `FileAccess.Open` / `File.ReadAllText`），用户零 bootstrap；合并方案要求用户自己写 IO 注入，新手踩坑面增大
7. **Cocos/H5 等说"复用 typescript.rs"是否真复用得了**：JS 项目可以直接 `import` 生成的 .ts 经过 tsc 编译；纯 JS 项目需要 `tsc --target es5 --declaration` 生成 .js + .d.ts。文档里给一句构建说明，不在工具里产 .js。
8. **Defold / Love2D 复用 lua.rs**：现有 lua.rs 是 Lua 5.1 兼容语法（`local T = {...}; return T`），Defold 用的就是 Lua 5.1，Love2D 是 LuaJIT（兼容 5.1）——直接吃。文档说明即可。

   - `expected/csharp_unity/` `expected/csharp_godot/` `expected/csharp_dotnet/`
   - `expected/gdscript/`
   - `expected/typescript/`
   - `expected/cpp/`
4. **真机冒烟**（pre-merge 前必须做）：
