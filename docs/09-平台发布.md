# 平台发布

工具链有两个发布产物（@03.1 三层架构）：

- **`tablet.exe`**（顶层）：单二进制双模式——零参数 / `--gui [--workdir=...]` 走 GUI；其它参数（含子命令 / `--help` / typo）转给内置的 `tablet-cli` lib。Jenkins 不需要，开发 / 策划装这一份就够。
- **`tablet-cli.exe`**（中层）：纯命令行，体积小、不依赖 slint 渲染栈。Jenkins / CI / 服务器自动化批处理推荐用这份轻量版。

兼容性目标不同：

- **CLI** 受限于 Rust stdlib，只看 OS 版本下限；不需要图形栈
- **GUI** 在 CLI 之上还要求 OS 提供窗口系统 + 一条可用的渲染路径（GPU 加速 / 系统软件 GPU API / Slint 自带 software renderer）

本篇先讲 CLI / GUI 各自的兼容矩阵和现实约束，再给可执行的发布建议。

## 1. CLI 平台兼容

`tablet-cli` 不依赖任何 GUI 栈，跟着 Rust stdlib 走：

| 平台 | 支持 | 备注 |
|------|------|------|
| Windows 10 / 11 (1809+) | ✅ | 主要测试平台；Tier 1 |
| Windows Server 2016+ | ✅ | Tier 1 |
| Windows 7 / 8 / 8.1 | ❌ | Rust 1.78（2024-05）起 stdlib 不再支持，加载即 0xC0000005；如需走 §4.2 双 target |
| macOS 10.13+ (High Sierra) | ✅ | Tier 1；release 脚本以 `MACOSX_DEPLOYMENT_TARGET=10.13` 限定下限 |
| Linux x86_64 (glibc) | ✅ | kernel 3.2+, glibc 2.17+ |
| Linux x86_64 (musl) | ✅ | release 脚本 `linux-cli-musl` 目标产全静态 CLI，老 glibc / Alpine / 容器 scratch 直接跑 |
| ARM64 各平台 | ⚠ 未测 | 仅 macOS arm64 用户偶发反馈可用 |

CLI 用作 CI / Jenkins 打包，命中的目标基本是现代 Linux server，无渲染兼容问题。

## 2. GUI 渲染后端

`tablet` 在 CLI 兼容矩阵之上多了一层"渲染路径"。一台机器要跑起 GUI，至少得有一条 OS → API → Slint renderer 的链路。

### 2.1 三条路径

```
应用 (tablet)
  │
  ├─→ renderer-femtovg ──→ OpenGL ES 2.0 上下文
  │                          │
  │                          ├─→ 硬件 GPU（最快）
  │                          └─→ 软件 OpenGL（Mesa LLVMpipe / WARP；OS 提供）
  │
  └─→ renderer-software ──→ CPU 自己算像素 → blit 到窗口
                            （根本不碰 OpenGL/D3D API）
```

slint 启动时按下面顺序尝试，第一个能初始化的就用：

1. femtovg + OpenGL 硬件 / 软件实现（看驱动）
2. software renderer（兜底）

只有当 OpenGL 上下文都创建不出来（极端环境）才会落到 software。

### 2.2 OpenGL 不是"哪都默认有"

常见误解。各平台的"出厂默认 GPU API"是：

| 平台 | 默认 GPU API | OpenGL 状态 |
|------|------------|------------|
| Windows 10 / 11 | D3D11 / D3D12 | **不在系统里**，需要显卡厂商驱动单独提供。Intel / NVIDIA / AMD 官方驱动都带；精简 Windows 镜像 / 老机器可能没装 |
| macOS | Metal | OpenGL 已 deprecated（10.14 起），最高停在 4.1，仍能用 |
| Linux | OpenGL（Mesa） | 默认即装 |

所以"OpenGL 哪都能跑"这个印象主要来自 Linux 视角。Windows 上 OpenGL 是显卡驱动顺带提供的副产品。

### 2.3 software renderer 不等于"没显卡场景"

slint software renderer 是**完全 CPU 算像素**，跟 OpenGL 没关系。它的兜底场景：

- 用户机器装的精简 Windows，不带 OpenGL DLL
- Linux 远程桌面 / VNC 没透传 GPU
- 没装 Mesa 软件 OpenGL（Linux server 镜像）
- WSL1 等无 GUI 子系统的环境

**虚拟机不在这个清单里**：VMware / VirtualBox 都给虚拟显卡（VMware SVGA3D / VirtualBox VBoxVGA），OS 视角看就是有 GPU、有 OpenGL 驱动；底下算的是 CPU（host 上 LLVMpipe），慢但能用。所以虚拟机里 slint 默认走 femtovg + 软件 OpenGL 是常态。

### 2.4 features 选择

`crates/app-slint/Cargo.toml`：

```toml
slint = { version = "1.16.1", default-features = false, features = [
    "std",
    "compat-1-2",
    "backend-winit",        # winit 窗口/事件后端
    "renderer-femtovg",     # OpenGL 硬件加速（默认走这条）
    "renderer-software",    # CPU 兜底：OpenGL 上下文创建失败时降级
] }
```

体积权衡：

- 只 `renderer-femtovg`（slint 默认）：体积最小；OpenGL 上下文失败直接黑屏
- 加 `renderer-software`（本项目选择）：+<1MB；GPU 路径全失效时仍能跑
- 改 `renderer-skia`（未启用）：+~15MB；macOS 走 Metal、Windows 走 D3D 体验更好；本工具 UI 不复杂，性价比低

### 2.5 SLINT_BACKEND 调试覆盖

slint 看环境变量 `SLINT_BACKEND` 强制指定后端，调试 GPU 问题时让用户：

```bash
SLINT_BACKEND=winit-software   # 强制 CPU 渲染
SLINT_BACKEND=winit-femtovg    # 强制 OpenGL
```

能跑 software 不能跑 femtovg，问题出在 OpenGL 路径（驱动 / 上下文）。两个都不能跑则不是渲染层问题。

## 3. 字体兼容

slint 字体走系统 fallback，不嵌入任何字体到二进制。中文字体在三大平台的现状：

| 平台 | 默认中文字体 | 状态 |
|------|------------|------|
| Windows | 微软雅黑 | ✅ 系统自带，无需额外配置 |
| macOS | PingFang SC | ✅ 系统自带 |
| Linux | 看发行版 | ⚠ 大部分 server / minimal 镜像不带；需安装 `fonts-noto-cjk` 等 |

emoji 字体 fallback 链：

- Windows / macOS：彩色 emoji 默认可用（Segoe UI Emoji / Apple Color Emoji）
- Linux：通常需要 `fonts-noto-color-emoji`

视觉退化策略：单色 Unicode 符号（▶▼☑☐●○）渲染最稳定，应作为关键功能图标的首选；彩色 emoji 仅作装饰。详见 @04.10。

## 4. 发布建议

### 4.1 Windows 发布

**静态链接 VC++ Runtime**，避免用户机器没装"VC++ 可再发行包"启动闪退：

`.cargo/config.toml`：

```toml
[target.'cfg(target_os = "windows")']
rustflags = ["-C", "target-feature=+crt-static"]
```

代价：二进制 +~1MB；收益：Win10+ 任意机器双击即跑。

### 4.2 Win7 双 target（可选，不推荐）

仅当确认有 Win7 用户群时才做。流程：

```bash
rustup target add x86_64-win7-windows-msvc
cargo build --release --target x86_64-win7-windows-msvc
```

警告（落实在发布说明里给用户看）：

- `x86_64-win7-windows-msvc` 是 [Tier 3](https://doc.rust-lang.org/rustc/platform-support/win7-windows-msvc.html)，每次升 Rust 版本可能突然炸（无 CI 保证）
- slint 1.16 没有官方测过 Win7；winit / rfd / arboard 的 Win API 调用是否有 Win8+ 才有的全凭运气
- GPU 路径几乎肯定要走 software renderer（Win7 默认 OpenGL 1.1 软实现）
- 必须 `+crt-static` 静态链 VC++ Runtime
- 每次发布前需在 Win7 SP1 真机回归一次

如果项目内只有 1-2 个同事还在用 Win7，**升级他们的成本远低于维护两份 build**。

### 4.3 macOS 发布

- 默认 Tier 1 即用，无特殊配置
- arm64 机器需 `cargo build --target aarch64-apple-darwin`，或开 universal binary（`cargo-bundle` / `lipo`）
- **最低部署目标 10.13 (High Sierra, 2017)**：release 脚本 `build_macos()` 把 `MACOSX_DEPLOYMENT_TARGET=10.13` 导出到环境后再编。不设的话默认跟宿主一致（runner 通常 13.x），10.13 用户启动会被 dyld 拒；想再降只能换更老的 Rust，已不划算
- Gatekeeper：未签名应用首次启动需用户右键「打开」绕过；正式发布需 Apple Developer ID 签名 + 公证

### 4.4 Linux 发布

- 目标 glibc：≥ 2.17（CentOS 7 / Ubuntu 14.04 之后即满足）
- 桌面环境：X11 / Wayland 任一都行（winit 自适配）
- 系统依赖：fontconfig（字体 fallback）、libGL（OpenGL 软件实现）；server 镜像可能要 `apt install libgl1 libfontconfig1 fonts-noto-cjk`
- **musl CLI 单独发**：release 脚本 `linux-cli-musl` 目标只编 `tablet-cli`，target = `x86_64-unknown-linux-musl`。产出的二进制全静态，老 glibc / Alpine / 容器 scratch 直接跑，不挑发行版。tablet 没法走这条路——X11 / Wayland / fontconfig 都是动态库，musl 全静态会拖出一坨 build 链路问题，得不偿失。需要 GUI 仍用 glibc 目标
- 构建机需要 `apt install musl-tools`

### 4.5 推荐 release 命令

日常本地编译：

```bash
# 主流 Win/macOS/Linux 三平台
cargo build --release -p tablet-slint    # 顶层产物：GUI + CLI fallback
cargo build --release -p tablet-cli      # 中层产物：仅 CLI（Jenkins 用）

# 产物
target/release/tablet(.exe)        ← 装一份给开发 / 策划，零参数 / --gui 走 GUI、其它参数走 CLI
target/release/tablet-cli(.exe)          ← Jenkins / 自动化批处理用，体积小不依赖渲染栈
```

正式发布走 `scripts/release.sh <target>`（详见 `scripts/README.md`），按宿主一台 runner 编自家目标，**不做跨编译**。可选 target：

| target | 宿主 | 产物 |
|--------|------|------|
| `windows` | Windows | `dist/windows/{tablet,tablet-cli}.exe`（`+crt-static` 静态链 VC++ runtime） |
| `windows-win7` | Windows + nightly | `dist/windows-win7/...`（Tier 3，§4.2 双 target） |
| `linux` | Linux | `dist/linux/{tablet,tablet-cli}` |
| `linux-cli-musl` | Linux + `musl-tools` | `dist/linux-cli-musl/tablet-cli`（仅 CLI，全静态） |
| `macos` | macOS | `dist/macos/{tablet,tablet-cli}`（lipo 合并 intel + arm64 universal，最低 10.13） |
| `host` | 任意 | 自动按宿主跑所有可跑目标 |

release profile（@05.9）按性能优先编译，一次完整 build 2-4 分钟。

### 4.6 subsystem 选择 + 双击启动黑闪

`tablet.exe` 编译为 **console subsystem**（不加 `windows_subsystem = "windows"` 属性），三平台行为：

| 平台 | 二进制格式 | subsystem 概念 | 表现 |
|------|----------|--------------|------|
| Windows | PE | 有（GUI / console） | console subsystem，CLI 模式 stdout 与 cmd 同步 |
| Linux | ELF | 没有 | shell 直接 wait()，与普通 CLI 工具一致 |
| macOS | Mach-O | 没有 | 终端启动同 Linux；`.app` 双击走 launchd 不附终端 |

为什么不用 GUI subsystem？
- GUI subsystem 下 cmd 一启动 PE-GUI 程序就立刻返回 prompt，CLI 模式 stdout 与 cmd 提示符竞争 → 用户看到"没反应、要回车一次才出输出"
- AttachConsole(ATTACH_PARENT_PROCESS) 是运行时调用，**改不了 PE 头**，在 cmd 视角竞争已经发生
- 唯一稳妥的修法是改 console subsystem 让 cmd 同步等待，GUI 分支启动后立刻 FreeConsole 释放 console

代价：**Windows 双击启动会有 < 50ms 黑窗口闪烁**——console subsystem 程序进程启动瞬间，Windows 必然分配 console 句柄，PE 头层无法关闭。FreeConsole 在 main 顶端调，但闪烁时间客观存在。Linux / macOS 没 subsystem 概念，零影响。

实现：

```rust
// crates/app-slint/src/main.rs

#[cfg(windows)]
fn detach_console_for_gui() {
    use windows_sys::Win32::System::Console::FreeConsole;
    unsafe { FreeConsole() };
}

#[cfg(not(windows))]
fn detach_console_for_gui() {}

fn main() -> anyhow::Result<()> {
    let args: Vec<String> = std::env::args().collect();
    match classify(&args) {
        Route::Gui { workdir } => {
            detach_console_for_gui();      // 仅 GUI 分支释放 console
            run_gui(workdir)
        }
        Route::Cli => {
            // CLI 分支不调 FreeConsole，让 stdout 直挂父 cmd
            tablet_cli::run_with_args(&forwarded) ...
        }
    }
}
```

依赖（仅 Windows）：

```toml
[target.'cfg(windows)'.dependencies]
windows-sys = { version = "0.59", features = ["Win32_System_Console"] }
```

`tablet-cli.exe`（layer 2 独立 bin）天然就是 console subsystem，没有黑闪也没竞争——这就是把它单独发布的最大理由：Jenkins / 自动化批处理用 `tablet-cli.exe` 完全无感，`tablet.exe` 的 CLI 模式是"懒得装两份时的兜底"。

> 后期若把 `tablet-core` 暴露成 cdylib（@03.1 未来扩展），发布物会增加 `tablet_core.dll` / `libtablet_core.so` 与一份 cbindgen 生成的 .h，本文档届时同步增补。

## 5. 已知不支持

| 平台 | 原因 |
|------|------|
| Windows 7 / 8 / 8.1 | Rust 1.78 stdlib 不再支持；可走 §4.2 Tier 3 双 target |
| Windows XP / Vista | Rust 早就不支持，无可行路径 |
| macOS < 10.13 | release 脚本以 10.13 为下限；10.12 及更老需自己降 `MACOSX_DEPLOYMENT_TARGET` 并接受 Rust 旧版限制 |
| Linux glibc < 2.17（GUI） | stdlib 下限；CLI 走 `linux-cli-musl` 静态二进制即可 |
| WSL1 | 无 GUI 子系统，CLI 可用 |
| 纯 server / 无桌面环境 | GUI 不适用，CLI 可用（推荐 `linux-cli-musl` 静态版） |

CLI 在所有 §1 矩阵列出的平台都能用，是无桌面环境的兼容下限。
