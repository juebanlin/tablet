# 核心功能

本文档描述**核心层**（数据子系统）能力：在 .tbl 数据模型之上、**不依赖 UI** 即可完整运行的所有功能。CLI 模式（`tablet-cli`）是这些核心功能的薄入口，与 GUI 共享同一份 `tablet-core`。

涵盖范围：

| 类别 | 子项 |
|------|------|
| 项目与模板 | Project 目录结构 / .tblschema 模板（内置 + 本地 + 网络）/ 模板实例化 |
| 导出（核心 → 外部） | JSON / XML / xlsx / Java / Go / Lua / GDScript / TypeScript / C++ / C#（dotnet+unity+godot） |
| 导入（外部 → 核心） | xlsx → GroupPatch（应用到内存模型；UI Excel 桥接 @06 用） |
| 验证 | 全项目离线校验，CI 友好 |
| 测试数据生成 | 内置 / 外部 schema 灌随机或空数据，便于压测和 review |

UI 端（@06-UI 设计 / @07-Slint 实现）和 CLI 都是核心层的薄前端，行为完全一致。

## 1. Project（项目）

一个 Project = 一份独立的配置数据集。同一仓库可并存多个 Project（如 `slg-test` / `slg-prod` / `mini-game`），各自隔离的 schema + 数据 + 元数据。UI 一次性加载所有 Project 同时展示在 TreeSection 顶层（@04.2.0），跨 Project 直接通过右键复制/粘贴迁移节点。

### 目录结构

```
<repo-root>/
├── tablet.toml                       ← 仓库全局配置（所有 Project 共享）
└── projects/
    ├── slg-test/                       ← Project ID（[a-z0-9_-]{1,32}）
    │   ├── project.toml                ← Project 级专属配置（仅 [export] 段），缺失字段由全局配置补全
    │   ├── project.tblschema           ← 该 Project 的元数据（id/name/category/version）+ 结构骨架 + separators
    │   ├── config/                     ← 数据文件（.tbl）—— 当前 Project 范围内的源
    │   │   ├── hero/HeroBase.tbl
    │   │   ├── hero/HeroType.tbl
    │   │   └── global/GlobalConst.tbl
    │   └── .tbl-cache/                 ← Excel 桥接缓存（.gitignore，详见 @06）
    │       └── hero.xlsx
    ├── slg-prod/
    │   └── ...
    └── mini-game/
        └── ...
```

`project.toml` 字段：

```toml
[project]                           # 必有：Project 元数据
id = "slg-test"
name = "SLG 测试配置"
created_at = "2026-05-31T10:00:00Z"
source_template = "full"             # 来源模板 id（手动新建可省）
source_template_version = "1.0.0"

# 以下为可选段：项目级专属配置（仅 [export] 段）
# [export.server.java]
# package = "com.slg.test"
# code_output = "gen/slg-test/java"
```

加载时用全局配置作为模板，补全项目配置中的缺失字段，形成完整的运行时配置。

### 全局配置 vs Project 元数据

| 文件 | 范围 | 内容 |
|------|------|------|
| `<repo-root>/tablet.toml` | 仓库全局（`GlobalConfig`） | 默认类型分隔符（仅作新建空项目种子，@01.7.4）、全局导出配置、UI 偏好、`[project]` 记录上次进入的 Project 及打开列表 |
| `projects/<id>/project.toml` | 单个 Project | 该 Project 的可选 `[export]` 段（项目级专属配置），不含 `[ui]` / `[separators]`（前者用全局，后者用 schema） |
| `projects/<id>/project.tblschema` | 单个 Project 元数据 | id / name / category / version（项目身份）+ 结构骨架 + separators（项目级分隔符，优先级最高） |

`projects/` 下的 Project 列表由启动时扫描得出，**不需要**在 `tablet.toml` 里枚举。配置模板：加载时用 `GlobalConfig` 补全 `project.toml` 的缺失字段，`schema.separators` 作为分隔符唯一来源 → 形成 `project.config`（完整配置，业务逻辑使用）。详见 @03.4。

### 多 Project 同时管理

UI 一次性加载 `<repo-root>/projects/` 下**全部** project，TreeSection 顶层节点 = 每个 project 根（@04.2.0）；CLI 用 `--project <id>` 限定操作范围（list / export / new-project）。**不存在"切换 project"概念**——所有 project 始终在内存里，跨 project 复制/粘贴节点直接通过右键即可。

| 维度 | 行为 |
|------|------|
| 节点定位键 | `(project_id, group, name)` 三元组，`ProjectEngine.find_table` / `validation_errors` 等都按该键索引 |
| 引用范围 | `@TableName` / `@EnumName` 仅在同 project 的 `groups` 内解析；跨 project 引用产生验证错误 |
| 跨 project 节点迁移 | 右键复制 → 切到目标 project 的节点上右键粘贴；`@ref` 字段保持原值，未在目标 project 解析时按验证错误暴露 |
| 启动展开策略 | 仅 `tablet.toml [project].last_project` 指向的 project 默认展开，其它 project 折叠；展开状态会话内有效（不持久化） |
| 新建 group / table 落点 | 默认落到选中节点所在 project；空选时落第一个 project；project 根节点右键「新建 Group」可显式选 project |

`ProjectEngine` 持有 `Vec<Project>`，每个 `Project` 自带独立的 `project_root` / `config` / `schema` / `groups`。`[project].last_project` 字段语义为"启动展开偏好"——仍写入但不控制"切到哪个 project"（所有打开的 project 同时在内存中）。

### Project 保存 / 导出

| 入口 | 范围 |
|------|------|
| 工具栏 [保存] | 一键落盘所有脏 project |
| 工具栏 [导出] | 全部 project 各走自己的 `export_root`（多 project 模式下每个 project 各自隔离 `gen/`） |
| Project 根节点右键「保存此 project」 | 仅落盘该 project 的脏改 |
| Project 根节点右键「导出此 project」 | 仅导出该 project |

### ProjectEngine 路径解析

每个 `Project` 持有 `project_root: PathBuf`（指向 `projects/<id>/`），不再绑定仓库级 `config_dir`。所有路径基于该 root：

| 资源 | 路径 |
|------|------|
| schema | `<root>/project.tblschema` |
| 数据目录 | `<root>/config/` |
| 元数据 | `<root>/project.toml` |
| Excel 缓存 | `<root>/.tbl-cache/` |

### 老结构迁移

老仓库的根目录 `config/` 在新版本启动时**自动迁移**到 `projects/default/`：

- 移动 `config/` → `projects/default/config/`
- 把仓库内已有的 `*.tblschema`（如有）合并为 `projects/default/project.tblschema`
- 生成 `projects/default/project.toml`（空或仅含 [export] 段；身份信息在 project.tblschema）
- 在 `tablet.toml` 写入 `[project] last_project = "default"`

迁移一次性完成，不保留双结构；废弃根 `config/` 路径。

### 配置模板机制

v1.2.3 重构后，项目配置采用模板式填充，不是运行时继承：

**加载时的一次性补全**：
```rust
project.config = merge_config(
    global_config.export,      // 全局配置作为模板
    project_toml.export,       // 项目级专属配置
    schema.separators,         // 分隔符（最高优先级）
)
```

**配置原则**：
- 项目配置中有值的字段：使用项目值
- 项目配置中缺失的字段：由全局配置补全
- 运行时：所有逻辑直接使用 `project.config`（已补全的完整配置）
- 不保留 `raw_config` 字段（已在 commit 5b9762d 移除）
- 分隔符：`schema.separators` 作为唯一来源，覆盖任何 toml 配置

**示例**：
```toml
# 全局配置（tablet.toml）
[export]
encoding = "utf-8"
line_ending = "lf"

[export.server.java]
package = "com.game.config"
code_output = "gen/server/java"

# 项目配置（projects/slg-test/project.toml）
[export]
encoding = "gbk"  # 项目级专属设置

[export.server.java]
package = "com.slg.test"  # 项目级专属设置

# 最终生效配置（加载时补全）
project.config.export = {
    encoding: "gbk",                    // 来自项目配置
    line_ending: "lf",                  // 来自全局配置（补全）
    server.java.package: "com.slg.test", // 来自项目配置
    server.java.code_output: "gen/server/java", // 来自全局配置（补全）
}
```

### 单项目模式迁移

v1.2.3 已移除单项目模式兼容代码，统一为多项目架构：
- 启动时扫描 `projects/`，旧仓库的 `config/` 自动迁移到 `projects/default/`
- `ProjectState` 枚举：`Loaded`（已落盘）/ `Pending`（待保存）
- 清理了 `root_pending_create` bool 等迁移残留

## 2. 项目模板（Schema Template）

**项目模板** = `.tblschema` 文件，描述一份 Project 的结构（不含数据）。新建 Project 时从模板库选一个模板，工具按 schema **实例化**空的 `.tbl` 文件集合。

### 模板格式

`.tblschema` 文件的完整规则在 @01.10。要点：

- 头部 `# @meta key: value` directive 行提供模板元数据：`id`（路径标识 `[a-z0-9_-]{1,32}`）/ `name`（显示文本，含中文）/ `category`（分类筛选，如 test / slg / rpg）/ `version`（semver）/ `created_at`（项目创建时间，模板侧通常空）/ `source_template` + `source_template_version`（项目来源模板锚点）/ `has_preset`（derive 字段，按实际 sections 重算）—— 完整字段表见 @01.10.1
- 头部可选 `# @sep key = value` directive 行嵌入项目分隔符配置（25 leaf，仅与默认不同的字段才输出，详见 @01.7.4 / @01.10.3）
- 主体：多个 `[group/Name] mode` 段，每段下接字段定义行
- 段内可选 `# @preset` 数据块（详见 @01.10.5）：Table 段写示例数据行，Constant / Enum 段强制把条目写在 preset 块里（schema 主体不允许直接的数据行）
- 「模板不含数据」是历史表述——新机制下 Constant/Enum 必须用 preset，Table 是否带 preset 由 `has_preset` 标记控制

### 模板来源

工具支持三种模板源，统一通过 `TemplateSource` trait 访问：

| 来源 | 实现 | 路径 / 取得方式 | 加载时机 |
|------|------|---------------|---------|
| 内置（Builtin） | `BuiltinTemplates` | 编译时 `include_str!("../schemas/*.tblschema")` | 永远存在 |
| 本地（Local） | `LocalTemplates` | 程序根目录 `<binary-dir>/tblschema/` 下的任意 `.tblschema` | 启动扫描 |
| 网络（Remote） | `RemoteTemplates` | GitHub registry index.json + 各 .tblschema 拉到本地缓存 | 按需下载（@07 S15-H 后置）|

接口：

```rust
trait TemplateSource {
    fn list(&self) -> Vec<TemplateMeta>;          // 列出该源的全部模板（不读 body）
    fn load_by_id(&self, id: &str) -> Option<TemplateContent>;
}
```

### 内置模板

`crates/core/schemas/*.tblschema` 通过 `include_str!` 嵌入二进制，`build.rs` 把 `schemas/` 加进 rerun-if-changed。当前内置：

| id | 用途 |
|----|------|
| `standard` | 标准范式覆盖（所有类型 / 所有 mode），generate-test 默认源、回归测试驱动 |
| `sanguo` | 三国题材完整 demo：10 套枚举 + 8 张 Table + 1 张 Constant，全部带 `# @preset` 数据 |

后续可扩展（如 `slg-base` / `rpg-base`）：文件直接放进 `crates/core/schemas/`，build.rs 自动重编。

### 本地模板

`<binary-dir>/tblschema/` 目录下任意 `.tblschema` 文件——启动时扫描列表，metadata 不全的按文件名兜底（@01.10.1）。用户拷贝文件即可扩展模板库，不依赖工具版本，社区分享友好。

### 模板实例化

`instantiate_template(schema, target_dir)` 把 schema 翻译为空 `.tbl` 文件集合，写入 target_dir：

| schema 段 | 输出 |
|-----------|------|
| `[group/Name] table` | `<target>/config/<group>/<Name>.tbl`：写好 `#!tbl v2` / `#mode table` / `#desc` / `#export` / `#type` / `#field` / `---`，**数据行为空** |
| `[group/Name] constant` | `<target>/config/<group>/<Name>.tbl`：写好 `#!tbl v2` / `#mode constant` / `---`，每条常量行 `name | type | <empty value> | export | desc` |
| `[group/Name] enum` | `<target>/config/<group>/<Name>.tbl`：写好 `#!tbl v2` / `#mode enum` / `---`，**枚举条目直接写入**（来自 schema） |

同时把 schema 自身（去掉 `# @meta` 头）拷贝为 `<target>/project.tblschema`，作为该 Project 的结构定义。

实例化失败（schema 解析错误 / 目标目录非空）就报错回滚，不写半成品。

### 导出当前 Project 为模板

工具栏「导出为模板」入口（@04.6.7）：

1. 弹窗勾选要导出的 group / 节点
2. 编辑模板 metadata（id / name / category / version，预填项目 meta）
3. 选输出位置（默认 `<binary-dir>/tblschema/<id>.tblschema`）
4. 写出 `.tblschema`：合并所选段为一份 schema，加 `# @meta` 头

输出后自动出现在「本地」模板 tab，下次新建 Project 即可选用。

### CLI 入口

```bash
tablet-cli list-templates                                       # 列出内置 + 本地模板
tablet-cli list-projects                                        # 扫描 projects/ 列出全部 Project
tablet-cli new-project --template full --id slg-test            # 用模板新建 Project
                    --name "SLG 测试配置"
tablet-cli --project slg-test export                            # 用 --project 显式选要导出的 Project（不传 = 全部）
```

> CLI 端没有"切换"概念；`--switch-after` 标志已废弃。`new-project` 会更新 `[project].last_project` 到新 project（仅作为下次启动的展开偏好），但不影响其它 project 的存在。

GUI 端弹窗（@04.6.6 / @04.6.7）共享同一套底层逻辑。

## 3. 目录扁平化

**Group 仅工具内部使用**（树形导航 + `projects/<id>/config/<group>/` 子目录）。**生成产物不保留 group 层级**，所有配置项扁平输出。

| 产物类型 | 路径 | 说明 |
|---------|------|------|
| JSON 数据 | `gen/server/data/json/HeroBase.json` | 不分 group 子目录 |
| XML 数据 | `gen/server/data/xml/HeroBase.xml` | 同上 |
| Java Tpl | `gen/server/java/com/game/config/tpl/HeroBaseTpl.java` | 集中到 `tpl/` 子包 |
| Java 框架 | `gen/server/java/com/game/config/{ITpl,TplHolder,...}.java` | 框架与 Tpl 物理隔离 |
| Go | `gen/server/go/config/hero_base_tpl.go` | flat package（已有） |
| Lua | `gen/client/HeroBase.lua` | 不分 group 子目录 |

理由：
- 生成代码是给程序员消费的，他们只关心 `import HeroBaseTpl`，不关心配置工具里这个表归在哪个 group
- 配置项跨组唯一（验证规则保证），扁平后无命名冲突
- Group 不进入生成路径 → group 名允许包含中文（不会破坏 Go package / Java import）

registry key 同步简化：从 `"hero/HeroBase"` → `"HeroBase"`（与文件名一致）。

## 4. 导出选项

导出分为多个独立操作，可自由组合执行。CLI flag 与每个操作一一对应：

| 选项 | 说明 | 默认输出目录 | 状态 |
|------|------|-------------|------|
| JSON | 将 .tbl 数据导出为 JSON | gen/server/data/json/ | ✅ |
| XML | 将 .tbl 数据导出为 XML（JDK 7+ 原生解析） | gen/server/data/xml/ | ✅ |
| xlsx | 每 Group 一个 xlsx，用 Excel 编辑 / 审阅 / 配色 | gen/excel/ | ⚠️ 待开发 |
| Java | 生成 Java 接口 + Tpl 类 + TplHolder | gen/server/java/ | ✅ |
| Go | 生成 Go 结构体 + 加载框架 | gen/server/go/ | ✅ |
| Lua | 生成 Lua 文件，数据内嵌，require 即用 | gen/client/ | ✅ |
| GDScript | 生成 GDScript const dict（内嵌模式，Godot 4.x） | gen/client/gdscript/ | ✅ |
| TypeScript | 生成 `.ts`（内嵌模式，Node/Cocos/H5 通用） | gen/client/typescript/ | ✅ |
| C++ | 生成 C++ 头文件 + Loader（nlohmann/json，C++17） | gen/server/cpp/ | ✅ |
| C# (.NET) | 生成 C# schema 类 + Loader（System.Text.Json） | gen/server/csharp/ | ✅ |
| C# (Unity) | 生成 C# schema 类 + Loader（Newtonsoft.Json + Resources） | gen/client/csharp_unity/ | ✅ |
| C# (Godot) | 生成 C# schema 类 + Loader（Godot.Json + FileAccess） | gen/client/csharp_godot/ | ✅ |

枚举（mode=enum）**不参与数据文件导出**——枚举内容固定写死在生成代码里。

### 平台映射约定（不新建导出器，复用既有产物）

| 目标平台 | 复用 | 理由 |
|---------|------|------|
| Kotlin（Ktor / Spring Boot） | `--java` | Kotlin/JVM 100% 互操作 Java，Kotlin 把 `getX()` 自动暴露为 `obj.x` 属性访问，业务无感 |
| Defold / Love2D | `--lua` | 现有 Lua 5.1 兼容语法直接吃 Lua 5.1（Defold）+ LuaJIT（Love2D） |
| Cocos / 自研 H5 | `--typescript` | TS/JS 项目都能 `import` 生成的 `.ts`；纯 JS 项目用 `tsc` 编出 `.js` |

C# 三 runtime（dotnet / unity / godot）**共享 schema 类**（`<Name>Tpl.cs` / `<Name>Enum.cs` 字段定义完全一致），仅 `Loader.cs` 的加载入口与 JSON 库不同——分别为 `System.Text.Json` / `Newtonsoft.Json` / `Godot.Json`。配置上以 `csharp_dotnet` / `csharp_unity` / `csharp_godot` 三个独立 key 区分（避免后期三 runtime 出现差异时被迫合并），CLI `--csharp` 一次同时生成三套。

以上目录为默认值，可在 tablet.toml 中修改：

```toml
[export]
encoding = "utf-8"       # 全局默认编码
line_ending = "lf"       # 全局默认换行符

[export.json]
empty_as = "null"
# line_ending = "lf"     # 可选，覆盖全局
# encoding = "utf-8"     # 可选，覆盖全局

[export.xml]
empty_as = "empty"
# line_ending = "lf"
# encoding = "utf-8"

[export.server]
data_output = "gen/server/data"
# line_ending = "lf"     # server 层级默认值
# encoding = "utf-8"

[export.server.java]
package = "com.game.config"
code_output = "gen/server/java"
lombok = true                    # 默认 true：@Getter 代替手写 getter（只出注解，不带 jar）
# custom_regions = true          # 默认 true：产物带业务扩展保留区间，重新导出时留住手写代码；不需要就设 false
# line_ending = "lf"     # 可选，覆盖 server → export
# encoding = "utf-8"

[export.server.go]
package = "config"
code_output = "gen/server/go"
# custom_regions = true          # 同上；Go 的区间落在文件末尾（方法必须是文件作用域的）
# line_ending = "lf"
# encoding = "utf-8"

[export.server.cpp]
namespace = "game::config"
code_output = "gen/server/cpp"
json_lib = "nlohmann"            # 仅 nlohmann 已实现；rapidjson 选了会在导出时报错
# custom_regions = true          # 同上
# line_ending = "lf"
# encoding = "utf-8"

[export.server.csharp_dotnet]
namespace = "Game.Config.Server"
code_output = "gen/server/csharp"
# custom_regions = true          # 同上；Unity / Godot 两个 C# 段各自也有这个键

[export.client.lua]
output = "gen/client"
# line_ending = "lf"
# encoding = "utf-8"

[export.client.gdscript]
output = "gen/client/gdscript"

[export.client.typescript]
output = "gen/client/typescript"

[export.client.csharp_unity]
namespace = "Game.Config.Client"
code_output = "gen/client/csharp_unity"

[export.client.csharp_godot]
namespace = "Game.Config.Client"
code_output = "gen/client/csharp_godot"
```

编码和换行符的 fallback 链：各部分独立配置 > 上级节点（如 `[export.server]` / `[export.client]`）> `[export]` > 默认值（lf + utf-8）。

UI 上提供：
- "全部导出"按钮 — 一键执行全部
- 菜单中可单独选择某一项执行

## 5. JSON 导出策略

JSON 数据文件包装为 `{"_sep": {...}, "data": [...]}` 结构，`_sep` 嵌入项目的分隔符配置供 Java 端解析复合类型。

**按需输出**：`_sep` 只包含该表/常量**实际用到**的分隔符 key（按字段范式聚合），跟字段无关的 leaf 不输出。全 base 表（无 List/Set/Map/Tuple/复合）直接**省略 `_sep` key**，文件就是 `{"data": ...}`。消费端模板的 `SepConfig.fillDefaults()` 给缺失的 key 兜底默认值，省略安全。

基础类型（int/long/float/double/bool）输出为 JSON 原生类型，复合类型（List/Set/Map/Tuple）保持原始分隔符字符串形式。

空值策略通过 `[export.json] empty_as` 配置：

| 策略 | 行为 | 示例 |
|------|------|------|
| `null`（默认） | 空值字段输出为 JSON null | `{"id":1, "hp":null}` |
| `omit` | 空值字段不写入 JSON | `{"id":1}` |

## 6. XML 导出策略

XML 数据文件使用原生 JDK DOM API 可解析的格式（JDK 7+ 零依赖）。分隔符配置嵌入根元素属性，attr 名 = `"sep_" + json_key`。

**按需输出**：与 JSON 同语义——根元素只挂该表/常量**实际用到**的 `sep_*` attr，全 base 表根元素**完全不带 sep_ attr**。

空值策略通过 `[export.xml] empty_as` 配置：

| 策略 | 行为 | 示例 |
|------|------|------|
| `empty`（默认） | 空值字段输出为空元素 | `<hp></hp>` |
| `omit` | 空值字段不输出 | 无该元素 |

## 7. 代码模板加载策略

生成的 Java/Go 代码加载 JSON 时，对空值（null 或字段缺失）统一按**默认值策略**处理：

| 类型分类 | 空值处理 | Java | Go |
|---------|---------|------|----|
| 基础类型 | 零值 | int=0, boolean=false, String="" | int32=0, bool=false, string="" |
| 集合类型 | 空集合 | new ArrayList<>() | []T{} |
| 元组类型 | 不会出现 | — | — |

- 不使用包装类型（Integer/*int），字段永远有值，业务代码无需判空
- 元组类型由验证层保证非空，加载时不需要处理空值情况
- 详见 [@01.8.4 空值规则](01-tbl系统.md#84-空值规则)

## 8. 命名规则

生成的类名/文件名与 .tbl 文件名一致，使用**大写驼峰**（Tpl 后缀仅 Table/Constant；Enum 用 Enum 后缀）：

| .tbl 文件名 | Java 类名 | Go 文件名 | Lua 文件名 | JSON | XML |
|-------------|-----------|-----------|------------|------|-----|
| HeroBase.tbl (table) | HeroBaseTpl | hero_base_tpl.go | HeroBase.lua | HeroBase.json | HeroBase.xml |
| GlobalConst.tbl (constant) | GlobalConstTpl | global_const_tpl.go | GlobalConst.lua | GlobalConst.json | GlobalConst.xml |
| HeroType.tbl (enum) | HeroTypeEnum | hero_type_enum.go | HeroType.lua | — | — |

上面是**类名 / 文件名**的规则。**字段名 / 常量名 / 枚举条目名**到各语言的转换规则（含 Lua 为什么保持 snake_case、枚举条目名为什么不转换）见 @01.8.1。

## 9. 导出规则

JSON 数据文件和后端模板类是给 server 用的，仅包含"前后端"和"服务器"标记的字段。Lua 前端文件直接从 .tbl 读取生成，仅包含"前后端"和"客户端"标记的字段。

| export 标记 | 数据文件 (JSON/XML) | 后端模板类 (Java/Go) | 前端文件 (Lua) |
|-------------|---------------------|---------------------|----------------|
| 前后端 | 生成 | 生成 | 生成 |
| 服务器 | 生成 | 生成 | 跳过 |
| 客户端 | 跳过 | 跳过 | 生成 |
| 不导出 | 跳过 | 跳过 | 跳过 |

枚举（mode=enum）的所有条目对所有目标语言生成（条目无 export 标记）。

### 字段注释

生成代码里的字段/属性都带 .tbl 里的 `desc`，各语言用各自的注释语法：

| 语言 | 注释位置与形式 |
|------|----------------|
| Java | 字段上方 `/** desc */` |
| C# | 属性上方 `/// <summary>desc</summary>` |
| TypeScript | interface 字段上方 `/** desc */`；常量是值字面量，说明跟在该行值后 `// desc` |
| Go | 字段行尾 `// desc` |
| C++ | 字段行尾 `// desc` |
| Lua / GDScript | 导出物是纯数据字面量、没有字段声明位，说明统一放文件头 `-- 字段：name=desc, ...` |

`desc` 为空的字段不写注释。Go / C++ 的字段注释**没有 `desc` 时退回 `TblFieldType` 串**（如 `// List<int>`），方便对照源类型。

## 11. 导出产物同步

每次导出时，工具对比生成目录中已有文件和本次应生成的文件，自动同步：

| 状态 | 含义 | 操作 |
|------|------|------|
| 新增 | 之前不存在的文件 | 写入 |
| 修改 | 内容有变化 | 覆盖 |
| 不变 | 内容相同 | 跳过 |
| 删除 | 目录中存在但本次不再生成（.tbl 已删除/重命名） | 删除文件 |

### CLI 行为

默认删除多余文件，打印变化日志：

```
[JSON] 2 新增, 1 修改, 1 删除, 3 不变
  [新增] gen/server/data/json/hero/HeroSkill.json
  [修改] gen/server/data/json/hero/HeroBase.json
  [删除] gen/server/data/json/hero/OldTable.json
```

不变的文件不打印。

### UI 行为

弹窗展示变化列表（新增/修改/删除），确认后执行。操作日志窗口记录导出详情。

### 清理范围

- 只对**本次实际执行的导出格式**做残留检测
- 例如只导出 `--lua`，不会清理 JSON/XML/Java 目录
- 所有文件参与检测（包括框架文件如 ITpl.java、TplHolder.java）
- 同步后自动清理空目录

### 业务扩展保留区间

生成的类型里常要放一点手写业务代码——缓存读取、临时处理、枚举上的业务判断函数。
另写一套 `TplService` 或者直接改生成文件（然后被下次导出冲掉）都不理想，所以给产物加**保留区间**：

```java
public class ItemTpl implements ITpl {
    // …生成的字段与 getter…

    // <TBL-CUSTOM-BEGIN>
    // 业务扩展代码写在这里，重新导出时原样保留
    // <TBL-CUSTOM-END>
}
```

打开方式：`[export.server.java] custom_regions`（其余后端各自段里同名）。**默认开**——不配就带区间，不需要的人显式设 `false`。

**契约**（只有一条：标记是唯一约定）：

| 情况 | 行为 |
|------|------|
| 区间**内部** | 原样保留 |
| 区间**外部** | 一律重新生成，手改会被覆盖 |
| 标记写坏（只剩一个 / 顺序颠倒 / 重复） | 整文件重新生成 + **警告**（该文件的手写内容可能已丢） |
| 标记被整个删掉 | 当普通文件覆盖，静默——无从判断哪些是手写的 |
| 开关关掉了、但盘上还有带内容的区间 | 覆盖 + **警告**，因为内容无处安放 |
| 区间里只有默认提示 | 不警告（否则每次关开关都刷噪音） |

三条边界要知道：

- **改类型名 / 删表 = 文件删掉重建**，区间跟着消失。没有「把用户代码搬到新名字」这一步。
- **只保护区间内部**。想给一个类型加字段、加 import，仍然会被覆盖——那类需求要改 schema，不是改产物。
- **别把业务代码写成 gen 目录下的独立文件**：同步是按扩展名清扫的，下次导出会把它删掉。

区间落在**产物是真类型**的四个后端（Java / Go / C++ / C#）。TS / Lua / GDScript 的产物是数据字面量，放不了方法，所以不参与。每个后端的具体落点见 @11.3.4。

## 12. 生成后端模板类（Java）

### 接口定义

接口放在 package 根目录：

**ITpl.java：**

```java
package com.game.config;

public interface ITpl {
    int getId();
}
```

**IConstTpl.java：**

```java
package com.game.config;

public interface IConstTpl {
}
```

### types 子包 — 元组类型

范式里的 `Tuple2/3/4`（@01.7）在 Java 侧落到 `types` 子包，三个泛型类，字段固定为 `v1..vN`：

**Tuple2.java：**

```java
package com.game.config.types;

public class Tuple2<T1, T2> {
    public final T1 v1;
    public final T2 v2;

    public Tuple2(T1 v1, T2 v2) {
        this.v1 = v1;
        this.v2 = v2;
    }

    @Override
    public String toString() {
        return "(" + v1 + ", " + v2 + ")";
    }
}
```

`Tuple3` / `Tuple4` 同构，依次多一个泛型参数与字段。

### 包内其它生成文件

除 `tpl/` 下的 Tpl 实体类和 `types/` 下的元组类，package 根目录还会固定产出这套运行时（即使当前项目一张表都没用到也会生成）：

| 文件 | 作用 |
|------|------|
| `ITpl` / `IConstTpl` | Table / Constant 实体类实现的接口 |
| `TblSource` / `TblFieldType` | 类级 / 字段级注解（见下两节） |
| `TblDataSource` | 数据源抽象；实现有 `FileSystemTblDataSource`（读目录）和 `ClasspathTblDataSource`（读打进 jar 的资源） |
| `IJsonParser` / `IXmlParser` | 解析器接口，配默认实现 `SimpleJsonParser` / `SimpleXmlParser` |
| `TblUtil` / `TblMeta` | 反射赋值 + 解析出的行 / 常量数据载体 |
| `Paradigm` / `SepConfig` | [@01.7 TblFieldType](01-tbl系统.md#7-tblfieldtype-类型系统) 范式的运行时解析策略 + 分隔符配置 |
| `TblFieldMismatchHandler` | 「类字段缺 / 数据字段多」的处理策略（默认宽松） |
| `TblLoadLogger` | 加载日志接口（默认控制台） |
| `TplHolder` / `TplRegistry` | 统一查询入口 / 生成的 key → Class 注册表 |
| `Example.java` | 用法示例 |

### Table 模式 → Tpl 实体类

放在 `tpl/` 子包，实现 `ITpl`，类级 `@TblSource` 标识来源（含 group 元信息），字段级 `@TblFieldType` 描述 [@01.7 TblFieldType](01-tbl系统.md#7-tblfieldtype-类型系统)：

**HeroBaseTpl.java：**

```java
package com.game.config.tpl;

import com.game.config.ITpl;
import com.game.config.TblFieldType;
import com.game.config.TblSource;
import java.util.*;

@TblSource(group = "hero", name = "HeroBase", mode = "table")
@Getter
public class HeroBaseTpl implements ITpl {
    /** 英雄 ID */
    @TblFieldType("int")
    private int id;
    /** 名称 */
    @TblFieldType("str")
    private String name;
    /** 血量 */
    @TblFieldType("int")
    private int hp;
    /** 技能 ID 列表 */
    @TblFieldType("List<int>")
    private List<Integer> skills;

    // 其余 getter 由 @Getter 生成；这一个必须显式写（ITpl 声明了它）
    @Override
    public int getId() { return id; }
}
```

上面的 `@Getter` 来自 `[export.server.java] lombok`（**默认开**）。关掉它会把 `import lombok.Getter;` 和注解换回逐字段的 `public T getXxx()`，两种形态的取舍见 @11.3.4。

字段上方的 `/** desc */` 取自 .tbl 的 `desc`，各语言导出时都会带上（见 @9「字段注释」）。

`@TblSource` 的 `group` 字段保留 group 元信息（业务/工具可反射查询来源），但**不影响**类的 package 路径。

### Constant 模式 → Tpl 常量类

同样放在 `tpl/` 子包，实现 `IConstTpl`。

**Table 行 vs Constant 项 → Tpl 类的统一视角**

两种模式最终都生成一个 Tpl 实体类，区别只是「类的属性怎么来」：

| 模式 | 类的来源 | 属性的来源 |
|------|---------|------------|
| Table | 一张 `.tbl` 表 → 一个 `XxxTpl` 类 | 表的每一**列**（`FieldDef`）→ 一个 Java 字段 |
| Constant | 一个 `.tbl` 常量集 → 一个 `XxxTpl` 类 | 常量集的每一**行**（`ConstEntry`）→ 一个 Java 字段 |

字段级注解都用 `@TblFieldType(...)`，`value` 就是 [@01.7 TblFieldType](01-tbl系统.md#7-tblfieldtype-类型系统) 字符串。运行时 `TplHolder` 反射拿这个注解 + `TplUtil.fromMap()` 把字符串值解析为目标 Java 类型。

**`name` 属性只在「源字段名 ≠ Java 字段名」时生成**。数据文件的 key 是 `.tbl` 里的源名（snake_case），而 Java 字段名是 camelCase，反射按 `field.getName()` 取不到，所以要显式带上源名：

```java
@TblFieldType("int")                                  // 字段 id —— 两边同名，省略
private int id;
@TblFieldType(value = "int", name = "stack_max")      // 字段 stackMax —— 源名不一致，必须带上
private int stackMax;
```

**GlobalConstTpl.java：**

```java
package com.game.config.tpl;

import com.game.config.IConstTpl;
import com.game.config.TblFieldType;
import com.game.config.TblSource;

@TblSource(group = "global", name = "GlobalConst", mode = "constant")
@Getter
public class GlobalConstTpl implements IConstTpl {
    @TblFieldType("int")
    private int maxLevel;
    @TblFieldType("Tuple2<int,int>")
    private Tuple2<Integer, Integer> startPos;
}
```

字段名转换规则：.tbl 中的 snake_case（`max_level`）→ Java 中的 camelCase（`maxLevel`）。

### TplHolder — 统一查询入口

放在 package 根目录。启动时从 `TplRegistry`（工具生成时写入的 key → Class 映射）取到全部配置类，用注入的 `TblDataSource` 批量读原始数据，再按 `@TblFieldType` 反射赋值。

**加载入口**（数据源是必填参数，目录/classpath 只是它的两个实现）：

| 方法 | 说明 |
|------|------|
| `init(TblDataSource)` | 用 `TplRegistry` 里的生成注册表 |
| `init(TblDataSource, Map<String, Class<?>>)` | 显式传入注册表 |
| `init(TblDataSource, String... packages)` | 在生成注册表之外，再扫描指定包下的 `@TblSource` 类 |
| `initXml(String dir)` / `initJson(String dir)` | 语法糖：`new FileSystemTblDataSource(dir, ".xml" / ".json")` |

字段值统一以字符串形式从数据文件读取，通过 `@TblFieldType` 注解 + `TplUtil.fromMap()` 解析为目标类型；`init` 时会校验数据文件格式与声明的数据源格式是否吻合（避免 XML 数据喂给 `initJson`）。

**查询**：`get(Class<T>, int)` / `getAll(Class<T>)` / `getConst(Class<T>)`。

**热更新**：`reload(String key)` 单表重载；`reloadConfigs(List<String>)` 批量重载，返回旧缓存快照，出错可 `restoreCache(...)` 回滚。

**可插拔**（须在 `init` 前设置）：`setJsonParser` / `setXmlParser` / `setMismatchHandler` / `setLogger`。

registry key 是配置项名（与数据文件名一致），不含 group 前缀。

**业务使用示例：**

```java
import com.game.config.TplHolder;
import com.game.config.FileSystemTblDataSource;
import com.game.config.tpl.HeroBaseTpl;
import com.game.config.tpl.GlobalConstTpl;
// 或一次性 import com.game.config.tpl.*;

// 从目录加载（XML / JSON 二选一）
TplHolder.initXml("config/server/data");
// TplHolder.initJson("config/server/data");

// 数据打进 jar 时改用 classpath 数据源
// TplHolder.init(new ClasspathTblDataSource("config/server/data", ".json"));

HeroBaseTpl hero = TplHolder.get(HeroBaseTpl.class, 1001);
GlobalConstTpl consts = TplHolder.getConst(GlobalConstTpl.class);
```

## 13. 生成后端模板代码（Go）

Go 后端生成 **flat package**：所有文件平铺在 `[export.server.go] code_output` 指向的目录下，包名取自 `[export.server.go] package`。零反射，每张表/常量生成专用 `Get` 函数。

### Java vs Go：范式绑定的两条路线

两边都需要把 [@01.7 TblFieldType](01-tbl系统.md#7-tblfieldtype-类型系统) 字符串变成针对每个字段的解析逻辑，但绑定时机完全不同：

| 维度 | Java（运行时反射 + 注解驱动） | Go（编译期展开，无注解） |
|------|------------------------------|--------------------------|
| 范式信息载体 | `@TblFieldType("Tuple2<int,int>")` 字段注解 | Rust 生成器把范式直接翻成 Go 语句 |
| 解析时机 | 运行时反射读注解 → `TplUtil.parseField(raw, ann.value(), sep)` 通用解析 | 生成时已展开为定型表达式（`parseInt32` / `parseListInt32(raw, sep.List)` …） |
| 字段级范式标记 | 注解（参与运行时） | 行尾 `// int` 注释（仅给人看，运行时无意义） |
| 反射依赖 | 是 | 否 |
| 装箱 | 是（`List<Integer>`） | 否（`[]int32`） |
| 加新范式时改的位置 | `TplUtil.parseField` 一处 | Rust `parse_expr_for` + 生成的所有 .go 文件重新生成 |

两边产物在业务逻辑上**等价**，只是范式 → 解析代码的转换发生在不同阶段。

**Java：注解 = 数据**

```java
public class HeroBaseTpl implements ITpl {
    @TblFieldType("List<int>")
    private List<Integer> skills;
}

// 运行时：
TblFieldType ann = field.getAnnotation(TblFieldType.class);
field.set(obj, TplUtil.parseField(raw, ann.value(), sep));
```

**Go：范式 = 生成时已固化的语句**

```go
type HeroBaseTpl struct {
    Skills []int32 // List<int>   ← 注释，运行时无作用
}

func parseHeroBase(row map[string]string, sep SepConfig) *HeroBaseTpl {
    obj := &HeroBaseTpl{}
    if raw, ok := row["skills"]; ok && raw != "" {
        obj.Skills = parseListInt32(raw, sep.List)   // ← 范式编译期就定了
    }
    return obj
}
```

引用类型同理：Java 用 `@TblFieldType("@HeroType")` 反射判断 `field.getType().isEnum()` 调 `fromId`；Go 直接生成 `obj.Type = HeroTypeEnum(parseInt32(raw))`。

### Table 模式 → Tpl 结构体

**hero_base_tpl.go：**

```go
package config

type HeroBaseTpl struct {
    Id     int32   // 英雄 ID
    Name   string  // 名称
    Hp     int32   // 血量
    Skills []int32 // 技能 ID 列表
}

var HeroBase_data = map[int32]*HeroBaseTpl{}

func parseHeroBase(row map[string]string, sep SepConfig) *HeroBaseTpl {
    obj := &HeroBaseTpl{}
    if raw, ok := row["id"]; ok && raw != "" {
        obj.Id = parseInt32(raw)
    }
    if raw, ok := row["name"]; ok && raw != "" {
        obj.Name = parseStr(raw)
    }
    if raw, ok := row["hp"]; ok && raw != "" {
        obj.Hp = parseInt32(raw)
    }
    if raw, ok := row["skills"]; ok && raw != "" {
        obj.Skills = parseListInt32(raw, sep.List)
    }
    return obj
}

func init() {
    registerTable("hero/HeroBase", func(rows []map[string]string, sep SepConfig) {
        m := map[int32]*HeroBaseTpl{}
        for _, row := range rows {
            obj := parseHeroBase(row, sep)
            m[obj.Id] = obj
        }
        HeroBase_data = m
    })
}

func GetHeroBase(id int32) *HeroBaseTpl       { return HeroBase_data[id] }
func GetAllHeroBase() map[int32]*HeroBaseTpl  { return HeroBase_data }
```

字段名规则：.tbl 中 snake_case（`max_level`）→ Go 中 PascalCase 导出（`MaxLevel`），而**查表用的 key 仍是源名 `max_level`**——数据文件的 key 也是源名，全链路同名（@01.8.1）。

## 14. 生成枚举（mode=enum）

枚举固定范式（id|name|desc），无 export 标记，对所有目标语言全量生成。**枚举不参与数据文件导出**——内容固定写死在生成代码里。

### Java —— 真正的 enum + Javadoc desc + @TblSource

**HeroTypeEnum.java：**

```java
package com.game.config.tpl;

import com.game.config.TblSource;

@TblSource(group = "hero", name = "HeroType", mode = "enum")
public enum HeroTypeEnum {
    /** 战士 */
    WARRIOR(1, "战士"),
    /** 法师 */
    MAGE(2, "法师"),
    /** 弓手 */
    ARCHER(3, "弓手");

    public final int id;
    public final String desc;

    HeroTypeEnum(int id, String desc) {
        this.id = id;
        this.desc = desc;
    }

    public int getId() { return id; }
    public String getDesc() { return desc; }

    public static HeroTypeEnum fromId(int id) {
        for (HeroTypeEnum e : values()) if (e.id == id) return e;
        return null;
    }
}
```

- 类级 `@TblSource(group, name, mode = "enum")` —— 复用 Table/Constant 的注解，业务/工具可反射查询来源
- 每个常量上 Javadoc `/** desc */` —— IDE 悬停 `HeroTypeEnum.WARRIOR` 显示 `战士`
- `getId()` / `getDesc()` 与 Tpl 类的取值风格保持一致（枚举不实现 `ITpl`，这里只是给业务提供统一取值的入口）
- 业务用法：`HeroTypeEnum.WARRIOR.id` / `.desc` / `.getId()` / `.getDesc()` / `valueOf("WARRIOR")` / `fromId(1)`
- `valueOf(String)` 是 JDK 给每个 enum 自动生成的（按**常量名**查，未命中抛 `IllegalArgumentException`）；`fromId(int)` 才是工具生成的（按 **id** 查，未命中返回 `null`，反射加载器依赖它）

### Go —— typed int + 常量 + 行注释 + 反查函数

**hero_type_enum.go：**

```go

}

func ParseHeroTypeEnum(name string) (HeroTypeEnum, bool) {

```

## 16. 生成数据文件（JSON）

### Table 模式

**HeroBase.json：**

```json
{
  "_sep": {"list": ";"},
  "data": [
    {"id": 1001, "name": "战士", "hp": 100, "skills": "1;2;3", "type": 1},
    {"id": 1002, "name": "法师", "hp": 80, "skills": "4;5", "type": 2}
```

`_sep` 只包含表中实际范式用到的 leaf：HeroBase 仅 `skills: List<int>` 是复合范式，所以只写 `list`。其余 `id` `name` `hp` `type` 都是 base / Ref，不需要分隔符。如果整张表全 base / Ref（比如纯 int/str 的简单表），`_sep` 会**整个被省略**，文件直接是 `{"data": [...]}`。

### Constant 模式

**GlobalConst.json：**

```json

  "_sep": {"tuple2": ","},
  "data": {
    "maxLevel": 100,
    "startPos": "5,10"
  }
}
```

JSON 中字段名使用 camelCase，与 Java Tpl 类字段一致。基础类型输出为 JSON 原生类型，复合类型保持分隔符字符串。`_sep` 按需输出 —— 这里只有 `startPos: Tuple2<int,int>` 一个复合范式，所以仅写 `tuple2`；消费端 `SepConfig.fillDefaults()` 给缺失 key 兜底。

## 19. 生成 Excel 文件（xlsx）

每个 **Group** 可生成为一个 xlsx 文件；Group 内每个 Table / Constant / Enum 对应一个 sheet（tab）。这是**核心层能力**——CLI（`tablet-cli excel export ...`）和 UI（@06 Excel 桥接）共用一条路径。

### sheet 布局

| 模式 | 行结构 |
|------|--------|
| Table | 4 行表头：第 1 行 desc / 第 2 行 export（"前后端" / "客户端" / "服务器" / "不导出" 中文形式，便于策划阅读） / 第 3 行 type（如 `int`） / 第 4 行 field（字段名）<br>第 5 行起：数据，第 1 列固定为 id |

| Enum | 第 1 行：固定表头 `id / name / desc`<br>第 2 行起：数据 |

每个 sheet 顶部冻结表头行（Table 冻 4 行 / Constant + Enum 冻 1 行）便于策划滚动；表头开 sheet protection（无密码，防误改），数据区用 `unprotect_range` 整段解锁——策划只能改数据格，碰表头会被 Excel 拦下。

### 行颜色映射

⏸ 行颜色标记（`#@c:RRGGBB` ↔ xlsx 行背景色）当前未实现，作为独立任务 S14-Color 排期。

| GUI 「Excel 编辑」按钮 / Group 右键 | `<project_root>/.tbl-cache/<group>.xlsx`（自动） | 节点名 |

sheet 名直接用 `Table.name` / `Constant.name` / `Enum.name`，Excel sheet 名最长 31 字符且禁 `\ / ? * [ ] :`，`sanitize_sheet_name` + `unique_sheet_name` 处理转义和重名。

## 20. 导入 Excel 文件（xlsx → GroupPatch）

xlsx 解析回内存模型是**导出 xlsx 的反函数**，与导出共用 sheet 布局规则（行颜色未支持）。主要供 UI 端的 Excel 桥接（@06）调用——策划在 Excel 中改完关闭后，UI 触发解析并 apply 到内存。

### 解析规则

| 来源 | 目标 |
|------|------|
| sheet 名 | 必须与 group 内节点名一一对应（多 / 缺均拒） |
| Table 表头 4 行 | 与原 schema 逐格比对（desc / export / type / field）；任一格不一致 → `Err` |
| Table 列数 | 必须 = `schema.fields.len()`；否则 `Err` |
| Constant 表头 1 行 | 必须 = `["name", "type", "value", "export", "desc"]`；列数必须 = 5 |
| Enum 表头 1 行 | 必须 = `["id", "name", "desc"]`；列数必须 = 3 |
| 数据行 | xlsx 单元格全部 `to_string()`（Float 整数化、Bool / Int / DateTime 也转字符串），空尾行自动忽略 |

**严格 header 校验**的设计动机：xlsx 是「数据编辑器」不是「schema 编辑器」。schema 改动必须经 UI 走 .tblschema 流程，否则失去"工具内可见 + diff + 校验"。

### 错误回报

任一结构校验失败 → 整次拒绝，**不返回部分 patch**（要么全成要么全拒，避免半 patch 的不一致状态）。错误信息包含具体 sheet 名 / 列序 / 期望值 vs 实际值，UI / CLI 直接打到日志。

### 入口函数

```rust
// 节点补丁
pub enum NodePatch {
    Table { name: String, records: Vec<Vec<String>> },
    Constant { name: String, entries: Vec<ConstEntry> },
    Enum { name: String, entries: Vec<EnumEntry> },
}

pub struct GroupPatch {
    pub patches: Vec<NodePatch>,
}

pub fn import_xlsx_into_group(path: &Path, group: &Group) -> Result<GroupPatch>;
```

`apply_patch_to_group` 故意不放 core——core 模型对 group 的引用是借出去的，apply 是 GUI / CLI 的职责（决定 dirty / undo / 验证时机）。GUI 实现见 `crates/app-slint/src/excel_bridge.rs::apply_patch_to_group`。

实现位置：`crates/core/src/excel.rs`。底层用 `calamine` 0.35 读 xlsx。

### 20.1 Excel 同步引擎（`tablet_core::excel_sync`，独立功能）

§19 / §20 的 `excel.rs` 是**严格导出/导入桥**（xlsx ↔ .tbl 一一对应，header 严格校验）。与之**相互独立**的是 `excel_sync` 模块——GUI 同步面板的后端，负责**对比 + 选方向合并** `.excel/*.xlsx` 与内存 group：

形状是**两侧投影 → 决策 → 定点落盘**，四个子模块分工明确：

```text
Group ──投影──► SheetVo ─┐
                         ├── plan_group()（纯函数）──► GroupPlan ──┬──► 定点写入 Group
Workbook ─投影─► SheetVo ─┘                                        └──► 定点写入 Workbook ──► write
                                                                        （NOT: VO → 文件）
```

| 模块 | 职责 |
|------|------|
| `vo` | 两侧共用的行列表模型 `SheetVo`（列 + 行 + `range`）。**读取边界无损**；不承载样式 |
| `read` | `Group` / `Workbook` → `SheetVo`。只读，不写回 |
| `plan` | 决策：两侧 VO + schema → `GroupPlan`。**纯函数**，列对齐的黑盒只在这一个模块里 |
| `apply` | `apply::execute(path, group, node, op)` 把一次 `SyncOp` 作用到两个真相对象上 |

| API | 作用 |
|-----|------|
| `read_xlsx_sheets(path, group)` | 读 xlsx 全部 sheet → `Vec<SheetVo>`（value() 直接返字符串，避免 calamine 类型推断）。`group` 用于判定表头布局 |
| `tbl_sheet_vo(table)` | `Table` → `SheetVo` |
| `plan_group(group, sheets)` | 算出一整个 group 的 `GroupPlan`：每个配对的 `ops`（允许做哪些操作）、列对齐、差异标记 |
| `apply::execute(path, group, node, op)` | **重算计划 → 校验 op 仍合法 → 落盘**。面板过期就拒绝 |

**决策为什么是数据**：「显示什么」和「点下去做什么」原本是两条独立推导的路径（Slint 谓词算一个、Rust 的 action 分支算另一个），靠手工对齐；而 Rust 侧算好的那份分类是**没人读的死数据**。现在两边读同一份 `PairPlan`。`SyncOp` 的**内容就是它的身份**——面板回传操作本身而不是下标，否则文件一变下标就指向别处。

### sheet 布局与 desc

同步面板的 xlsx 用 **4 行表头**，与 §19 的导出布局逐格一致：

| 行 | 内容 | 策划能否改 |
|---|---|---|
| 1 | desc | ✅ **改这里** |
| 2 | export（中文展示值） | — |
| 3 | type | — |
| 4 | **列名** | ❌ 约定不改，列匹配靠它 |
| 5+ | 数据 | ✅ |

约定是「列名不改、desc 可改、颜色与高宽随便调」，而这份 xlsx 与 tbl 之间**只交换 desc + 数据**。所以同步是**双向**的：推送（tablet → xlsx）刷新表头四行 + 数据；回读（xlsx → tablet）带回 desc + 数据。desc 只取匹配前缀内的列，前缀之外的列本来就不参与同步。

`ColumnVo.desc` 是 `Option<String>`：`None` = 这一格不存在（旧布局整行都不存在），`Some("")` = 格在、内容是空的。**这个区分是必须的**——`None` 意味着回读时不动 tablet 的 desc，空 vec 或空串会把 desc 全抹掉。

**回读时「空 = 清空」**：匹配前缀内以 Excel 为准，空串一样覆盖。范围由 `matched_prefix` 表达，所以不再需要「空值不覆盖」那道守卫——它以前同时干着划范围和不覆盖两件事，害得策划在 Excel 里清空一个格、tbl 的值却清不掉。

**type / export 行的越权检测**：这两行按约定策划**不该**动。他改了要吭声（日志一句「已忽略」），不能静默忽略——那和本仓库已经栽过的几类「默默吃掉改动」同源。

**旧布局识别**：本特性之前生成的 `.excel/*.xlsx` 只有 1 行列名、数据从第 2 行起。按新布局去读会把 3 行数据当表头吃掉、数据整体错位，所以 `read_xlsx_sheets` 靠 schema 字段名判定：第 4 行吻合 = 新布局，否则第 1 行吻合 = 旧布局，两者都不吻合按新布局（列名被改坏，交给面板报「表头不符合规范」）。旧布局文件在**首次被推送时原地升级**成 4 行表头。

### VO 的两条边界

**区域由表头界定**：VO 的单元格区域 = **表头覆盖的列** × **（表头行 + 有效行）**，是一个矩形，不是「工作表用到的所有格子」。列名行最后一个非空格是第几列就有几列。区域之外的东西**不进 VO，但也不消失**——记在 `SheetVo.range` 里，`range.max_col > columns.len()` 就是「表头之外还有东西」的明确信号（只在日志里说一句，不在面板上提示）。

**列只能从 tbl 侧（schema）添加。** xlsx 里多出来的列一律不碰——既**不收进 schema**（那等于让 Excel 决定 schema），也不删（那是策划自己的测试列 / 公式列，@06 §7.2）。多出来的列**不记日志**：它是常态，每次都报就是噪音。

以前拿的是全表最大列：策划在 Z 列写一条备注就会把表头补成一串空格子、面板判成「xlsx 多列」然后**只给一个「强制→」**。

**不承载样式**：填充 / 字体 / 边框 / 列宽行高不进 VO。样式不是同步的交换物，而是必须**原样留存**的东西，留存的机制是 `apply` 的定点写入。把样式塞进 VO 会诱导出「VO → 文件」的序列化写法，那条路会毁掉保真。

### 保真：不动没被同步的 sheet

`apply` 的推送用 umya 的 **`lazy_read`**：只有被写到的 sheet 会被反序列化，其余 sheet 在写回时走 zip 层的**原始压缩字节直通**（umya 按 `is_deserialized()` 分流）。策划在别的 sheet 上做的一切因此原样保留。

代价是**被同步的那几张表**会丢掉 umya 没有建模的元素（行/列分组折叠、已应用的筛选条件等），详见 @06 §7.4。因此推送路径里不要为了「看一眼」去调 `sheet()` / `sheet_mut()`——那会把那张 sheet 一起拖下水。

实现位置：`crates/core/src/excel_sync/`（`mod` / `vo` / `read` / `plan` / `apply`）。底层用 **umya-spreadsheet**（读写保留已有格式化），与 `excel.rs` 的 calamine + rust_xlsxwriter 路线不同。仅 GUI 同步面板调用，CLI 未暴露。交互细节见 @06 §7。

## 21. 验证（CLI validate）

`tablet-cli validate` 触发**全项目离线校验**，是 @01.8 验证规则的 CLI 入口。GUI 端的"实时验证 / 保存校验"走同一份 core 逻辑（@03.4.10.2）。

### 命令

```bash
tablet-cli [-w <workdir>] [-s key=value]... validate
```

### 退出码

| 码 | 含义 |
|----|------|
| 0 | 全部 .tbl 通过四层验证（cell / row / schema / project，@01 附录 A） |
| 1 | 任一节点验证失败 / .tblschema 解析失败 / 文件读取失败 |

### 输出

stdout 打印每个问题一行（`format_validation_log`，与 GUI 日志同一套渲染），先错误后警告；每个 entry 自带位置、原值与消息。`--fmt json` 时 stdout 只有 JSON。

### 警告与错误（severity）

校验结果带级别（@01.10.7）：

| 级别 | 来源 | 默认动作 | 退出码 |
|------|------|---------|--------|
| `error` | 现有全部内置检查 + `[error]` 级 `# @rule` | 阻断保存 | 1 |
| `warn` | `[warn]` 级 `# @rule`、与系统校验重复的规则（`RuleRedundant`） | 仅提示 | 0 |
| `info` | `[info]` 级 `# @rule` | 忽略 | 0 |

**动作可由项目级策略覆盖**（`project.toml` 的 `[validate]`，@01.10.7）：每个级别可设为 `block` / `report` / `ignore`。CLI 的退出码、是否进错误列表都按这个策略走；`ignore` 的级别不产生任何结果。

`validate --strict` 把所有「仅提示」的条目也算作失败（有即 exit 1），CI 建议用它；本地开发可用默认行为，让「多语言表还没建」这类问题只提示。

CI 推荐用法：

```bash
tablet-cli validate --strict || exit 1
tablet-cli export        # 验证通过才导出
```

## 22. 测试数据生成（CLI generate-test）

`tablet-cli generate-test` 依据内置或外部 `.tblschema` 模板，生成 .tbl 数据 + 配套配置文件，供：

- 工具开发期对照测试（不需要真实策划数据）
- 新接入项目的脚手架（一键起一个空项目）
- 性能压测（生成 N 万行随机数据）

### 命令

```bash
tablet-cli generate-test \
  [--empty | --schema <path>] \
  [--rows N] [--seed N] \
  [--format json|xml] \
  [--lang java|go|none]
```

| 参数 | 说明 | 默认 |
|------|------|------|
| `--empty` | 生成空骨架（仅 schema，无数据行） | — |
| `--schema <path>` | 用指定 .tblschema 文件；缺省走内置 `full.tblschema` | 内置 |
| `--rows N` | 每张 Table 生成 N 行随机数据（与 `--empty` 互斥） | 5 |
| `--seed N` | 随机种子，方便复现 | 当前时间戳 |
| `--format` | 顺手把生成的项目导出一份数据文件 | json |
| `--lang` | 顺手把生成的项目导出一份代码 | none |

### 实现：复用模板模块

`generate-test` 内部分两步：

1. `BuiltinTemplates::load_by_id(<id>) → schema` —— 从模板模块拿 schema
2. `instantiate_template(schema, tempdir)` —— 实例化空 .tbl 文件集合
3. **填充随机数据**（generate-test 独有）—— 按 `--rows N` 在每张 Table 灌随机行，Constant 灌随机 value，Enum 已由 instantiate 写完不再处理

这样模板加载 / 实例化的逻辑在内置模板库（@项目模板）和测试数据生成之间复用。`--schema <path>` 模式直接读外部 .tblschema 文件并用同一个 instantiate 通路。

### 内置 schema

`crates/core/schemas/{full,empty}.tblschema` 通过 `include_str!` 嵌入二进制（`build.rs` 把 schemas/ 加进 rerun-if-changed，避免改 schema 不重编）。改 schema 必须保证通过 @01.8 验证（如字段名不能用 Java / Lua / Go 关键字）。

## 25. 内部数据模型

`tablet-core` 的运行时数据结构。GUI / CLI / 导出 / 验证全部基于这套类型工作；`actions/` 层只管在它们之上做编排，UI 层把它们映射到 Slint Model。结构定义在 `crates/core/src/{model,ops,validate}.rs`，本节描述字段语义，不复制代码原文。

### 25.1 ProjectEngine — 多 Project 工作空间

```rust
pub struct ProjectEngine {
    pub workdir: PathBuf,                            // 仓库根；tablet.toml / gen/ 所在
    pub global_config: GlobalConfig,                 // 仓库全局配置（来自 tablet.toml）
    pub available_projects: Vec<AvailableProject>,   // 扫 projects/ 得到的全部（含未打开）
    pub projects: Vec<Project>,                      // 已打开的 Project，按打开顺序
    active_idx: Option<usize>,                       // 当前 active 在 projects 里的 idx
    pub validation_errors: HashSet<(String, String, String, usize, usize)>,
                                                     // (project_id, group, name, row, col)
    pub node_clipboard: Option<NodeClipboard>,       // 进程内树面板剪贴板
    pub default_separators: SeparatorsSection,       // 「新建空项目」分隔符种子（来自 global_config）
    pub logs: Vec<String>,                           // GUI 日志框积压
}

pub struct AvailableProject {
    pub id: String,
    pub name: String,
    pub root: PathBuf,            // <workdir>/projects/<id>/
    pub created_at: String,       // schema.meta.created_at；用于 sort=created
}
```

`active_idx` 是私有字段，外部通过 `active() / active_mut() / set_active_by_id()` 访问。"按 (group, name) 定位节点"的接口隐式作用在 active 上，要求 UI 在 active=None 时不要触发。`global_config` 为所有 Project 共享，每个 Project 的 `config` 是加载时用全局配置补全项目配置缺失字段的结果。详见 @04.2.0（多 Project 树根模型）。

### 25.2 Project — 单 Project 内存表示

```rust
pub struct Project {
    pub workdir: PathBuf,            // 仓库根（与 ProjectEngine 一致）
    pub project_root: PathBuf,       // <workdir>/projects/<id>/
    pub config: ProjectConfig,       // 完整配置（加载时由全局配置补全），业务逻辑使用
    pub schema: TblSchema,           // project.tblschema 解析结果，承担"项目身份+结构骨架"双职
    pub groups: Vec<Group>,
    pub original_meta: SchemaMetadata,             // 上次落盘时的 meta 快照
    pub original_separators: SeparatorsSection,    // 上次落盘时的分隔符快照
    pub state: ProjectState,         // Loaded（已落盘）或 Pending（待保存）
}
```

`schema.meta.id / name / created_at / source_template* / category / version` = 项目身份；`schema.sections` = 结构骨架，由 ops 在 group/node 变动时增量同步。配置模板：加载时 `merge_config(global_config, project_toml, schema.separators)` 一次性补全 → `config`（完整配置）；`raw_config` 已在 v1.2.3 移除。

项目状态 `ProjectState` 枚举：
- `Loaded`：从磁盘加载的已存盘项目
- `Pending`：新建的未落盘项目（克隆、模板创建、空白新建），save 时先 create_dir_all 再写文件

### 25.3 Group / Table / Constant / EnumDef

```rust
pub struct Group {
    pub name: String,        // 文件夹名（允许中文）
    pub dir: PathBuf,
    pub tables: Vec<Table>,
    pub constants: Vec<Constant>,
    pub enums: Vec<EnumDef>,
    pub is_new: bool,        // 内存中新建、还未落盘
}

pub struct Table {
    pub name: String,
    pub path: PathBuf,
    pub schema: TableSchema,         // fields: Vec<FieldDef>
    pub records: Vec<Vec<String>>,   // 行 × 列；单元格统一以 String 持有
    pub dirty: bool,                 // 当前内存 != 上次保存时的序列化（update_dirty 重算）
    pub deleted: bool,               // 标记软删除，save 时 unlink
    pub original: String,            // 上次落盘的完整文本，用于 dirty 比较
}

pub struct TableSchema { pub fields: Vec<FieldDef> }

pub struct FieldDef {
    pub name: String,
    pub desc: String,
    pub tbl_type: String,            // 原文（@01.7 类型语法），仅在用时按需 parse_field_type
    pub export: Export,
}

pub struct Constant {
    pub name: String,
    pub path: PathBuf,
    pub entries: Vec<ConstEntry>,
    pub dirty: bool,
    pub deleted: bool,
    pub original: String,
}

pub struct ConstEntry {
    pub name: String,
    pub tbl_type: String,
    pub value: String,
    pub export: Export,
    pub desc: String,
}

pub struct EnumDef {
    pub name: String,
    pub path: PathBuf,
    pub entries: Vec<EnumEntry>,     // id|name|desc 三列固定
    pub dirty: bool,
    pub deleted: bool,
    pub original: String,
}

pub struct EnumEntry { pub id: String, pub name: String, pub desc: String }

pub enum Export { ClientServer, ClientOnly, ServerOnly, None }
```

四点说明：

1. **单元格统一 String**：所有类型在内存中以原文文本持有；语义解析（int / list / ref 等）按需在验证 / 导出时即时进行。这避免了"输入即解析"带来的中间态错误暴露，保留"红框 + 原文"的二态。
2. **dirty 用文本对比，不维护精细 dirty bit**：`update_dirty()` 每次重新序列化整个 .tbl 与 `original` 比较——简单且对 partial 编辑鲁棒。N 行的表算一次 dirty 是 O(N)，在万行量级仍在毫秒以内。项目层的 `schema_changed` 同理，由每层跟自己的盘上快照比出来（@26.2）。
3. **deleted 软标记**：删除节点先打标，由 `save` 阶段统一处理 unlink + 从 Vec 中移除，便于撤销和原子 save。**重命名走同一条路**（见 @26.1）：改名只写内存，`save` 时才搬文件。
4. **Export 四态**：ClientServer（前后端）、ClientOnly（客户端）、ServerOnly（服务器）、None（不导出）。空字符串和无效值默认解析为 ClientServer。详见 @01.10 schema 规则。

### 25.4 ProjectInstanceMeta — 项目身份元数据（已废弃）

```rust
pub struct ProjectInstanceMeta {
    pub id: String,
    pub name: String,
    pub created_at: String,                     // RFC3339 UTC
    pub source_template: Option<String>,        // 模板 id；空 / null = 空白创建
    pub source_template_version: Option<String>,

```

## 26. 节点状态与脏标记

UI 层（@04.2.2 TreeSection 节点状态）渲染节点上的"红圈 / `*` / `+`"标记：

| 状态 | 视觉 | 数据来源 |
|------|------|----------|
| 删除 | 红圈 | Table/Constant/EnumDef 的 `deleted: true` |
| 修改 | `*` | `dirty: true`，由 `update_dirty()` 对比落盘快照（records / fields / `original_name`，后者见 @26.1） |
| 新建 | `+` | `is_new: true`（Group）/ 节点 `path` 不存在于磁盘 |
| 错误 | `!` | `ProjectEngine.validation_errors` 中存在该 (project_id, group, name, *, *) |

聚合规则（沿 TreeSection 自下而上）：

- 节点本身的视觉按上面四种判定
- Group 节点：把内部 Table/Constant/EnumDef 的状态做或聚合
- Project 根节点：聚合所有 Group

`!` 在"项目结构操作"（新建 / 重命名 / 拷贝 / 删除节点 / 删除组）时无视 `realtime_validate` 开关，必然触发 `validation_errors` 索引同步：删除→清除残留 entries；重命名→平移 key；新建/拷贝→建立新索引。`realtime_validate` 仅控制单元格内容编辑路径的复算行为，详见 @03.4.10.2 / @01 附录 A。

### 26.1 重命名：保存时才动盘

**除重命名外，本工具在点"保存"之前不碰任何 `.tbl`。** 重命名曾经是唯一的例外——它在改名那一刻就 `fs::rename`，而 `project.tblschema` 没跟着写，于是"文件已经动了"与"还有东西没保存"同时成立：`*` 标记是真的（schema 确实跟盘不一致），但成因是这次改名**提交了一半**。现在它与 `deleted` 一样是软操作。

`Group` / `Table` / `Constant` / `EnumDef` 各有一个 `original_name`——**上次落盘时在盘上叫什么**。语义与已有的 `original_records` / `original_fields` / `original_entries` 一致：**只在 load 与 save 两个点写，改名时不动**。

这个"不动"是刻意的，它同时解决两件事：

| 情况 | 为什么成立 |
|------|-----------|
| 连续改名 A→B→C | `original_name` 始终是 `A`，而盘上确实还是 `A.tbl`。若记成"上一次改名前叫什么"，第二次改名就把 A 覆盖成 B，save 会去找一个不存在的 `B.tbl` |
| 组与组内节点同时改名 | 组记组的原名、节点记节点的原名，两级各推各的：旧位置 = `<group.original_name>/<node.original_name>.tbl`，新位置 = `<group.name>/<node.name>.tbl` |

**必须存名字，不能存旧绝对路径**：存的瞬间路径是对的（盘上没动），但 save 时一旦先搬了组目录，子节点记的那条路径就指向一个不存在的位置，正确性开始依赖"先搬谁"的执行顺序。存名字是无序的组合式推导。

`save_project_files` 在写入循环**之前**跑 `apply_pending_renames`，顺序是**先组后子**：组目录整个搬走时组内文件跟着走，叶子名没变的子节点到这一步就到位了。搬不动（文件被占用 / 没权限）就把内存退回去并返回一条警告，由 `save_all` 报到 UI 日志——宁可这次改名不生效，也不要内存说叫 B、盘上还叫 A。

`update_dirty()` 相应把 `original_name != name` 计入：

```rust
self.dirty = self.records != self.original_records
    || self.schema.fields != self.original_fields
    || self.original_name != self.name;   // 改名也是一次未落盘的改动
```

少了最后一条，改名后的节点在树上显示为"干净"。

**CLI 注意**：`schema rename-group` / `schema rename-node` 内部 `execute_action` + `save_all()`；因为搬文件推迟到了 save，验证不过时盘上什么都没动，这两个命令会据 `save_all()` 的返回值报错，不再对外声称"已重命名"。

### 26.2 脏是「我和盘上一致吗」——每层自己回答，UI 往上投影

`dirty` 不是一个"改过了"的标，而是**一个无损的事实**：这份数据和盘上一致吗。它必须由**每一层自己**回答，因为只有那一层知道自己的盘上快照；上层的脏是把下层**投影**上来，不另存一份。

这样才有正确的层次表现：`A.B.C` 里只改了 `C`，树上 A、B、C 都显示 🟡，而**实际只有 C 那个文件会写盘**。

三层各回答自己的问题：

| 层 | 自己的问题 | 快照 |
|---|---|---|
| `Table` | `dirty`（本 .tbl 要写吗）／ `schema_changed`（schema 要写吗） | `original_records` / `original_fields` / `original_name` / `original_display_field` |
| `Constant` / `EnumDef` | 同上 | `original_entries` / `original_name`（Enum 多一个 `original_display_field`） |
| `Group` | `is_dirty` = 自己 `is_new` / 改过名，或**任一子节点** | `original_name` + 子节点的答案 |
| `Project` | `is_dirty`（项目有东西要写吗）／ `schema_changed`（project.tblschema 要写吗） | `original_meta` / `original_separators` + 子层的答案 |

#### 叶子要答两个问题，不是一个

```rust
Table::schema_changed() = original_name != name || fields != original_fields
                        || original_display_field != display_field     // 不含 records
Table::update_dirty()   = dirty = records != original_records || schema_changed()
```

**必须分开**：改一个格子的值只让那个 `.tbl` 要写盘，`project.tblschema` 一个字都不用动。父层要是直接 OR 子节点的 `dirty`，**每次单元格编辑都会把 schema 标脏**。

（`original_display_field` 单列出来是因为 `# @display` 写在 schema 里却住在节点上；它是唯一喂给 `schema_from_project` 又没有天然快照的字段。**回填时也要一起填**——`apply_display_to_groups` 把 `# @display` 读回节点时若只填 `display_field`，刚打开的项目就会显示"改过"、永远亮 🟡。）

#### `schema_dirty` 这个字段已经删掉

以前它是个**手工贴上去的 bool**：`sync_schema_from_groups()` 在每个结构操作后无条件置 `true`，撕不掉，于是"改名 A→A1 再改回 A"会永久留下一个项目级的 🟡。

改成上面这套之后**没有可写错的标**——所有 `schema_dirty = true` 的写入点（结构操作、表头编辑、增删列、`# @display`、项目设置的 meta/separators、克隆）全部消失，因为每一处改动都已经落在某个 `original_*` 快照的对比里。

同理 `Project::original_schema`（一份完整的 schema 副本）也删了：`schema.sections` 是 groups 的投影（`schema_from_project` 只读组名 / 节点名 / 列定义 / `# @display`），拿它跟自己的副本比是把缓存和缓存比。项目**自己的属性**只有 `meta` 与 `separators`，`sections` 交给子层回答。

比较一律用**结构相等**而非序列化文本：手改过 `project.tblschema`（加注释、调顺序）不该被当成"脏"——按文本比那种项目一打开就永远亮着。

**新增喂给 `schema_from_project` 的字段时，要记得在对应层加快照**，否则那个字段的改动会静默不算数。`ops::tests::engine_with_saved_node` 走的真实链路（内存建 → save → 从盘上 load）并断言 `!loaded.is_dirty()`，漏了会红。

### 26.3 `project.toml`：可选覆盖段，改了才写

`project.toml` 里只有 `[export]`，它跟 `project.tblschema` 是**两个文件**，所以 `Project` 上有两个分开的问句（顺带各自一个快照）：

| 问句 | 管哪个文件 | 快照 |
|---|---|---|
| `schema_changed()` | `project.tblschema` | `original_meta` / `original_separators` + 子层 |
| `toml_changed()` | `project.toml` | `original_export` |

分开是必要的：改 export 不该顺手重写 `project.tblschema`，反之亦然。

**写盘规则：只在 `config.export` 真的变过时才写。** 没改过就不生成文件——文件缺席时 `parse_project_config` 让 export 从工作区 `tablet.toml` **继承**，所以改全局配置能传播到还没覆盖过的项目；一旦在「项目设置」里动过，这个项目就被冻住了（这是覆盖段的本意）。

两处曾经是错的：

1. **对话框里改的 export 从来没落过盘**。`project_settings::run` 只写内存的 `p.config.export`，而 `save_project_files` 只在 `project.toml` **不存在**时写一次——所以那个 🟡 是空头支票。
2. **首次保存写的是 `ExportConfig::default()`**，既不是项目的 `config.export` 也不是全局配置。而新建项目时 `config` 是从全局配置拷来的——于是"新建项目首次保存"会**静默把 export 配置重置成全默认**，重载后变味。现在写的是 `project_toml_text(&project.config.export)`。

「项目设置」这个对话框两半落在两个文件上，但**提交点是同一个**（保存）：`meta` / `separators` 进 tblschema，`[export]` 进 project.toml。不做成"确定即写盘"是因为：未落盘项目连 `project_root` 目录都没有（首次保存才建目录），而且同一个对话框里两个字段两种落盘时机没人能理解。全局设置的 `tablet.toml` 是**工作区级**、一定已存在，所以那边立即写没有问题。

**UI 树必须直接问实体，不要自己再拼一遍聚合。** 这条踩过坑：树的项目行原本是手工把"自己的 schema 变化 + 各子节点 dirty"OR 起来，加 `toml_changed()` 时两边不同步，于是"只改了 export 保存"不亮 🟡。现在项目行就是 `Project::is_dirty()`、组行就是 `Group::is_dirty()`——以后往这两个谓词里加东西，树自动跟上。（树的 `!saved` / `is_new` 那部分是人另外算的，因为它们决定的是 🟢 而不是 🟡，是另一种标记。）


### 26.4 还原到已保存——第一阶段的无历史撤销

「改错了只能重新加载」原本只有**整个工作区**级的出口（工具栏「重新加载」），代价是把所有未保存改动一起丢掉。现在有两个定点的出口，作用域一大一小：

| 位置 | 作用域 | 还原什么 |
|---|---|---|
| 表格区功能 bar 的 `[还原]` | 当前选中的节点 | `records` / `schema.fields` / `name` / `display_field` |
| 项目设置底部的 `[全部还原]` | 项目自己的属性 | `meta` / `separators` / `[export]` |

**两者都只是一个操作：把 `original_*` 写回状态。** 没有历史栈、没有 diff、没有逆操作。`Project::revert_settings()` 与 `Table` / `Constant` / `EnumDef` 各自的 `revert_to_saved()` 就是全部实现。

三条边界，都是刻意的：

1. **只管编辑，不管存在性。** 新建未保存的节点（`saved == false`）压根没有「盘上的样子」可还原，`[还原]` 置灰；软删的节点还原内容后**仍然是删着的**。存在性归右键的新建 / 删除管。
2. **还原必须走「写回状态」这条普通路径**，不能写成绕过状态的一次性副作用。将来做连续撤销时，这里就该变成一次普通的历史记录，不需要另开旁路。
3. **改名还原不需要任何文件系统动作。** 改名本来就只落内存、save 时才搬（@26.1），名字改回 `original_name` 等价于从没改过。

「全部还原」的可用状态是 `Project::settings_changed()`——**刻意不含 `groups`**：那个按钮还原不了数据改动，不该为数据改动亮起来。

#### 与将来的「连续撤销」是什么关系

不冲突，而且是它的前置条件。两者目标不同：「还原到已保存」的目标是一个**快照**，「连续撤销」的目标是一个**历史栈**。已定方向是**快照式**连续撤销（不是逐个记录 delta），而快照式的硬前提是「编辑区里每样东西都能算出一份快照、且能和快照比」——那正是 @26.2 的分层 `original_*` 加上本节建立起来的属性。

**要守的约定：凡是要能撤销的东西，都必须能从快照算出来。** 守住这条，将来连续撤销就退化成「把快照做成栈」，不用去每个编辑点埋钩子。

### 26.5 导出配置的 key 空间（`ExportKey`）

`ExportConfig` 是四层嵌套、每层都是 `Option`，UI 上有 29 个可编辑叶子。读 / 写 / 比对 / 还原四件事**共用一个 key 空间** `ExportKey`（`crates/core/src/export_keys.rs`）：

```
get(cfg) -> String              // 显示值（含各处 unwrap_or(默认) 的兜底）
modified(live, orig) -> bool    // 比 Option，不比渲染出来的字符串
set(cfg, v: &str) -> bool       // 人给的输入；非法值保持原样并返回 false
revert(&mut live, &orig)        // 精确复制那一个 Option
```

**为什么比的是 `Option` 而不是 `get()` 的字符串。** 这里有十几个叶子带非空默认（`lombok` 与六个 `custom_regions` 是 `unwrap_or(true)`，五个枚举是 `unwrap_or(default)`）。盘上是 `None`、现值是 `Some(默认值)` 时，两者**渲染出来一模一样**，但 `project.toml` 会多出一个键、项目确实脏了。只比字符串就会报「没改过」——于是出现「项目脏了、却没有任何字段是蓝的」。`revert` 同理：写成 `set(live, get(orig))` 会把 `None` 写成 `Some(默认值)`，**还原完还是脏的**。

**`revert` 要连着祖先链一起裁剪。** `set` 为了写一个叶子会造出祖先的 `Some(默认值)`；若只复制叶子本身，那个造出来的祖先会留着。规则是「先把祖先链裁剪成 `orig` 的形状、再复制叶子」——`orig` 某个祖先为 `None` 蕴含它底下每个叶子都是 `None`，所以整条撤掉是安全的。

**这个 key 空间是在补一个已经漏过的洞。** 原来 Slint 发裸字符串、Rust 手写 match 接，两边各写各的拼写，编译器管不着。实际漏了三个：`csdn_custom_regions` / `csu_custom_regions` / `csg_custom_regions` 发出来没有任何 arm 接住，被 `_ => {}` 吞掉，于是三个 C#「自定义区域」勾选框**点了没反应、自己弹回去**（项目设置与全局设置各一份）。现在认不出的 key 走 `error_log`，不再静默。

**全局设置那份也接上了**（@26.6）。它原本是**第三份**手写导出 match，而且和项目那份行为已经不一致（非法枚举：项目保留旧值 vs 全局设 `None`；空串：项目 `None` vs 全局 `Some("")`）——三个 C# 勾选框在那边同样点了没反应。现在两个对话框都走 `ExportKey::set`，这两处分歧一起消失。


### 26.6 全局设置：编辑缓冲 + 打开时快照

全局设置对话框（UI / 分隔符 / 导出）用的是**另一套参照物**，和项目设置不一样。根因是**提交点不同**：

| | 提交点 | 参照物住在哪 | 「内存 ≠ 盘上」的窗口 |
|---|---|---|---|
| 项目设置 | 「保存项目」 | 数据结构上的 `original_*` | **跨会话**（关掉再开还是蓝的，树上还亮 🟡） |
| 全局设置 | 「确定」**就是**写盘点 | 一个打开时的快照（`current_snapshot`） | **恰好是对话框开着的这段时间** |

所以全局设置不需要 `original_*` 字段——一个打开时的快照就够：关掉对话框，「不一致」就没有东西需要留存了。反过来说，那边的「还原」天然只在一个会话内有意义。

**但编辑缓冲必须留**（这点与项目设置相反，那边我们把 buffer 删掉了）：`engine.global_config` 是活的工作区状态，别的东西会读它（分隔符驱动校验、导出配置），而且它的 `project_management` 段自己不归这个对话框管。所以 `ui` / `sep` / `export` 三个 buffer 保留，只是角色从「撤销用的备份」变成「待应用的编辑」。

**按 tab 分块比，不能整份 `!=`。** `tablet.toml` 有**两个写入口**：这个对话框，以及拖项目排序（`crates/app-slint/src/ui/tree.rs` 的 `persist_global_config`）。后者改的是 `project_management` 段。整份比会让「拖一下排序」被误判成对话框里有未保存改动。

**刻意不做页面级「全部还原」**：全局设置的「取消」已经是它了（区别只是关不关窗）。反悔的入口是每个字段右侧的还原按钮。这是与项目设置的另一处不对称——那边去掉「取消」的理由是「关闭 ≠ 提交」；全局设置里「确定」就是落盘点，去掉取消等于「关窗即改工作区配置」，副作用比项目设置重得多（工作区级、立即生效，分隔符还会触发**全项目**重校验）。

UI 段的 8 个叶子走 `UiKey`（`crates/core/src/ui_keys.rs`），与 `ExportKey` / `SepKey` 同一套路子，共用 `config_leaf` 里那几个严格的取值 / 写值小工具。


### 26.7 读不懂就报错：`project.tblschema` 的失败契约

**核心：`project.tblschema` 存在但解析不了 = 打不开，不是兜底成空项目。**

原来这里是 `Err(_) => fallback`（`read_project_schema_with_fallback`），把解析错误整个吞掉，换成一个「空身份 + 默认分隔符」的空 schema。而数据是从 `.tbl` 另读的，所以项目**看起来一切正常** —— 直到下一次保存，把原始 schema 覆盖掉。CLI 主要由 AI / 脚本驱动，没有反馈就等于没有发生。

现在拆成两条：

| 场景 | 行为 |
|---|---|
| 文件**缺失** | 兜底空 schema（还没建 schema，不算"坏"） |
| 文件在、**解析失败** | `Err`，带**文件路径 + 行号 + 原因** |

两个前提条件：

1. **声明了 `# @meta id` 就必须合法**（`[a-z0-9_-]{1,32}`）。「没声明」仍然合法 —— 合并用的片段、裸 `.tblschema` 都不带 id（`merge_schemas` 也不挂 metadata），校验收紧了会把那条路一起打死。空值声明（`# @meta id:`）算非法，那是写坏了，不是"没声明"。
2. **扫描列表仍然宽松**：`project list` 要能列出坏项目（按目录名兜底），一个坏项目不该让整张列表打不开。真要动它的时候走严格路径，那时硬失败。

#### 两端的呈现

`load_workspace` **不自己决定怎么出声**，它把打不开的项目收集成 `Vec<ProjectOpenFailure>` 交出去 —— 因为 CLI 和 GUI 要的东西不一样：

| | 行为 |
|---|---|
| **CLI** | 逐条打 `错误: Project <id> 打不开: <文件>: line N: ...`，然后**非零退出**（`bail!` 经 `main.rs` 翻成 exit 1）。收口在 `dispatcher::load_workspace_checked` |
| **GUI** | 日志记一条（点掉之后还留得住）+ **弹提示框**（`AlertDialog`，只有一个「确定」）说明原因；那个项目**不打开**，其余照常 |

**例外：`project new` 不因为有别的项目打不开就拒绝。** 折腾坏了之后「建一个新的」正是出路之一，堵死它没有意义。

#### 同一条契约也管 `.tbl`

`load_group` 原来是 `Err(e) => eprintln!("warn: failed to parse {path}: {e}")` —— 一个写坏的 `.tbl`
在 stderr 留一行字，那张表就从项目里**整个消失**：`project info` 少一张、`export` 少一个文件、
退出码还是 0。现在解析失败直接 `Err`（带文件路径与原因），走与 schema 完全相同的两端口径。

顺带把两个「用错了却一片绿」的入口收掉：

| 入口 | 以前 | 现在 |
|---|---|---|
| `validate --group/--node <不存在>` | "验证通过" + 0（空集恒真） | 非零 + `Group 不存在: xxx` |
| `export data --group/--node <不存在>` | 0 个文件 + 0 | 非零 + 同上 |

`# @preset` 行的**列数超过声明**也一并拦下：Table 超过字段数、Constant 超过 5 列、
Enum 超过 3 列都带行号报错。`apply_schema_to_project` 用的是 `Vec::resize`，
多出来的列会被截断且不吭声 —— 「复制一行多带一个 `|`」就少一个值。少写仍然允许
（缺的位置按空处理，这是自然的写法）。

以及 schema 写命令的一整套闸门（先校验、再看 `save_all()` 返回值、先查目标是否存在），
详见 @03.8.2 与 @03.7.4。

`AlertDialog` 与 `ConfirmDialog` 分开：后者问「要不要做某事」（取消是个真实选择），前者报告「已经出事了，看一眼」（没有可取消的动作）。也不复用 `pending` 那套 confirm —— 它的开关由 `pending.action` 驱动，任何一次 `refresh::after_ctx_menu` 都会把它按 pending 的状态关掉。


### 26.8 Xlsx 组：一组一个工作簿

**动机**：策划不想用工具、只想在 Excel 里改。Xlsx 组让工作簿本身成为真相源，
工具退化成"能读能写这个工作簿的编辑器 + 导出器"。

#### 模型

一组一种后端（`GroupStorage`），不混存：

| 组类型 | 结构真相源 | 数据真相源 | 落盘位置 |
|---|---|---|---|
| `Tbl`（默认） | 各 `.tbl` 自己（自描述） | 各 `.tbl` | `config/<group>/<Node>.tbl` |
| `Xlsx` | **`project.tblschema` 的 section** | **workbook 的 sheet** | `config/<group>/<group>.xlsx` |

节点（`Table` / `Constant` / `EnumDef`）在内存里两种后端完全同型，差别只在
**加载时从哪读、保存时往哪写**——所以 validate / export / 代码生成 / 网格全部免费。

后端由目录里有什么决定：有 `<group>.xlsx` 就是 Xlsx，否则 Tbl；两者同时存在 → 报错（不猜）。

#### 加载

- 先读 `project.tblschema`，把 section 交给 `load_groups_in`。
- **schema 有 section、workbook 没有同名 sheet → 打不开**（不兜底成空表）；
- workbook 有 sheet、schema 没有 section → 忽略（策划的私有 sheet；"托管节点"留到后续版本）；
- sheet 名与 section 名大小写不敏感地匹配（Excel 的口径）；
- Table sheet 必须是 **4 行表头**（desc / export / type / 字段名），列按**字段名**对齐；
  字段在表头里找不到就报错。`desc` 以 sheet 为准回填，`type` / `export` 以 schema 为准。

#### 保存

三条铁律，来自实测（见下）：

1. **不脏就不碰文件**——`is_new` / 任一节点 `dirty` / 有删除，三者都不成立时直接返回。
2. **一次会话写完整组**——每开一次文件都会重打整个 zip，逐节点写等于反复重打。
3. **只写脏 sheet**——`lazy_read` + 只对要写的 sheet 调 `sheet_by_name_mut`，
   其余 sheet 走 zip 原始字节直通。

写盘顺序：`tmp` 文件 → `rename`（避免半截 workbook）。写前两道闸：

- `~$<group>.xlsx` 存在（Excel 正开着）→ 拒绝保存；
- 加载时记下的 `(mtime, size)` 与当前不符（外部改过）→ 拒绝保存，交给用户重载 / 覆盖 / 另存。

新工作簿自带一个占位 sheet；组里一旦有节点就把它删掉（保留名 `_empty`，
段名必须大写开头所以不可能撞名）。删空整组时连工作簿和目录一起清掉，与 Tbl 组同语义。

**失败的保存什么都不写，包括 `project.tblschema`。** 两道保证：

1. 动盘之前先跑一遍全部 xlsx 组的预检（锁 / 外部改动 / sheet 名长度），有一个不过就
   整次保存取消——连接名和 schema 都不动；
2. schema 的写入挪到**组循环之后**，且只在没有组失败时执行。schema 是 groups 的投影，
   先写它、再发现组写不进去，就会造出「schema 里有这个节点、盘上却没有数据」，
   项目当场打不开。

#### 字节稳定性实测（决定上面三条）

umya 的写回是"重打整个 zip + 打当前时间戳"，实测结论：

| 场景 | 结果 |
|---|---|
| 外来文件（另一个库写）`lazy_read` + 原样写回 | 文件字节变；两个 sheet 的 **CRC 不变**，其余 9 个条目被重写 |
| 同上但用 `read()` 全量 | **连没改的 sheet 也被重序列化** |
| 只改一个格子 | 只有那张 sheet 的内容变；其它 sheet 的 CRC 不变 |
| 同样的编辑再做一次 | 所有 CRC 相同，只有 zip 时间戳差几秒 |
| umya 自己造的文件原样写回 | 11 个条目里 10 个字节相同，`sharedStrings.xml` 多 1 字节 |

推论：
- "顺手保存"一定会改字节 → **干净时零写入**（git 才不会平白多一个改动）。
- `lazy_read` 只反序列化碰过的 sheet → 没碰的 sheet 保真；这条是红线，有测试钉住。
- 首次接管外来文件会做一次规范化改写（`styles.xml` 的 tableStyles 默认值、
  `workbook.xml` 的 `calcPr`/`fullCalcOnLoad` 会变）——所以**第一期只支持工具自己创建的组**，
  导入外部文件另做阶段。

#### 外部修改与刷新

xlsx 组的前提是"策划随时可能在 Excel 里改完保存"，所以界面必须跟得上：

- GUI 每 1.5s 对所有 xlsx 组做一次 `stat`（mtime + size），与加载时记下的快照比；
- **干净组** → 自动从磁盘重载，刷新树 / 网格 / 日志；
- **有未保存改动** → 不重载，只提醒一次；组右键的「从磁盘重新加载」是显式的丢弃入口
  （带确认框）；正在编辑单元格时也不重载；
- 保存路径上的「外部已修改」拦截是最后一道闸——轮询没赶上也不会覆盖；
- 进程之间由工作区锁（`.tablet.lock`）互斥：GUI 与 CLI 不能同时操作同一个工作区（@03.7.5）。

跨后端粘贴：复制一个组后，粘贴有两种目标——「粘贴为 .tbl Group」/「粘贴为 Excel Group」。
节点在内存里两种后端同型，所以这是"换一个保存写入器"，不是数据转换（见 `paste_group_as`）。

#### 限制

- sheet 名 ≤31 字符（段名超限在保存时报错，不截断）；
- 不加 sheet protection：umya 不认识 `protectedRanges`，保留保护开关会变成整张只读（@06 §7.4）；
- 删字段不删 Excel 列（策划的私有列一律不碰）；列顺序以表头名字为准，不做重排；
- 「用 Excel 打开」= 先落盘再开原文件；Tbl 组的临时本桥接（@06）与同步面板都不作用于 Xlsx 组。

#### 后续阶段（未实现）

- 导入外部 Excel：托管组 + 逐 sheet 映射迁移（选类型、选 id 列、就地插入 4 行表头）；
- 跨后端复制粘贴的完整校验（目前能工作，按 sheet 规则校验名字留给 P2）；
- 整组转换存储后端（破坏性，需备份 + 确认）；
- 模板 / `project new --from-file` 表达后端（schema 文件里目前没有存储方式信息）。

## 27. RefIndex 跨表索引

`@Xxx:id` 引用类型（@01.7 [TblFieldType](01-tbl系统.md#7-tblfieldtype-类型系统)）需要在校验时回答"id=N 在 Xxx 表里是否存在？"。每次 cell 校验都扫一次目标表 = O(行数 × cell 数)，万行表会卡死。RefIndex 把这次扫描预计算成 O(1) 查询：

```rust
pub enum RefKind { Table, Enum, Constant }

pub struct RefIndex {
    map: HashMap<String, (RefKind, HashSet<String>)>,    // name → (kind, 有效 id 集)
}

impl RefIndex {
    pub fn build(groups: &[Group]) -> Self;              // 全量扫一次
    pub fn lookup(&self, name: &str) -> Option<&(RefKind, HashSet<String>)>;
    pub fn contains(&self, name: &str, id: &str) -> bool;
}
```

构建时机（在 `validate.rs::project_validate` 与 `actions/validate.rs` 顶部）：

- 项目级 `revalidate_all` 入口处构建一次，传入下层 cell / row 校验
- 单 cell 编辑且 `realtime_validate=true`：每次按键都重建（万行表也只是几毫秒）
- 项目结构变化（新建/重命名/拷贝/删除节点）：触发后重建

不增量维护——简单的全量重建已经足够快，且避免增量代码的复杂边界（id 改名、表删除、循环引用等）。

`Constant` 也进 RefIndex：当 `[ui] constant_ref_allowed = true`（默认）允许 `default_hero = @HeroType:1` 这种语法时，常量值也按 ref 校验，需要查 RefIndex；置 false 时 RefIndex 仍构建（其它 ref 列要用），但 constant 段里的 `@Xxx` 会被 schema 校验直接拒绝（ConstantRefForbidden）。详见 @03.4.10。
