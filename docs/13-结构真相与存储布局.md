# 结构真相与存储布局（计划）

> 状态：设计/计划文档。Phase 1（xlsx 组扁平布局）已实现，待验收；v4-lite 与 manifest/template 仅记录方案，未排期。

## 1. 问题

当前同一个项目里，结构信息可能出现在三处：

1. `.tbl` 的 `@field` 块（字段名 / 类型 / export / desc）；
2. `project.tblschema` 的 section（同一份字段 + 规则 / 引用 / display）；
3. 原生 xlsx 组工作簿的 4 行表头（desc / export / type / field）。

三条 Excel 编辑路线又各自持有表头：

| 路线 | 数据归属 | 表头角色 |
|---|---|---|
| Excel 桥接 / 临时本 | `.tbl` 组 | 生成视图；回读严格比对 |
| Excel 同步面板 | `.tbl` 组 | 生成视图；只交换 desc + 数据 |
| 原生 xlsx 组 | workbook | 离线编辑锚点；与 schema 比对 |

问题不是“表头存在”，而是**结构真相源是否唯一**。本文件把可选演进拆成三个维度，避免把 v4、双形态和存储布局混成一次改动。

## 2. 三个维度

### 2.1 维度 A：现状 v3（保留 `.tbl` 表头）

```text
#!tbl v3
#mode table
---
@field name
  desc:英雄名
  export:cs
  type:str
[1001]
  name:战士
```

- 结构真相源：`.tbl` 自己的 `@field`；保存时重写 `project.tblschema` 投影。
- 优点：`.tbl` 自描述，AI/人手改不需要先读 schema；Excel 表头与 `.tbl` 表头语义一致。
- 代价：结构元数据在 `.tbl` 与 schema 重复；schema 单独改动时需要同步两份。

### 2.2 维度 B：v4-lite（删 `.tbl` 表头，schema 唯一结构真相）

```text
#!tbl v4
#mode table
---
[1001]
  name:战士
  hp:100
```

- `.tbl` 只留 `[id] 字段名:值`，不再有 `@field` / 四行头；Constant / Enum 仍用 v2。
- 结构真相源：`project.tblschema`。
- 优点：结构只留一份；字段/export/type 改动不碰数据文件；数据 diff 仍然干净。
- 代价：`.tbl` 不能脱离 schema 单独解释；`util parse-tbl` / `fmt` / `diff` / skill 需要 schema；v3 硬切。

### 2.3 维度 C：manifest + template（运行时 schema 去掉表头）

保留 `.tbl` / workbook 自描述，把 schema 拆成两种明确形态：

1. **完整模板（可迁移导入）**
   - 带字段、类型、export、desc、preset 数据；
   - 用于模板库、跨项目导入、`schema export --as-template`。
2. **运行时 manifest**
   - 只保留项目身份、group/node 清单、storage、跨节点引用、`# @rule`、`# @display`；
   - 不保存表头；字段元数据从 `.tbl` / workbook 读。

```text
# 运行时 manifest（示意）
#!tblschema v2 manifest
[hero/HeroBase] table
# @rule: name = unique()
[building/Building] table xlsx
```

- 优点：运行时无表头重复；`.tbl` 继续自描述；模板仍可带数据迁移。
- 代价：两套 schema artifact / 版本头；所有读 schema 的工具都要先合并数据侧结构；xlsx 组结构必须明确来自 workbook。
- **前置条件**：xlsx 组必须是根级文件 `config/<group>.xlsx`；manifest 阶段再由 schema 显式记录 storage，否则“目录 / workbook / section”三者无法稳定对应。

## 3. 推荐决策

| 目标 | 推荐 |
|---|---|
| 没有明确结构漂移痛点 | 保持维度 A，不引入新格式 |
| 想要“结构唯一真相源”，接受硬切 | 维度 B（v4-lite） |
| 想保留 `.tbl` 自描述 + 模板可迁移 | 维度 C，但先做 xlsx 扁平布局 + manifest 实验 |

当前不把 B / C 直接落地。先完成 Phase 1：**xlsx 组扁平化**。这样 C 的后续讨论有稳定基础；B 随时可以在其之上做。

## 4. Phase 1：xlsx 组根级文件

### 4.1 目标布局

```text
projects/<id>/
├── project.tblschema
└── config/
    ├── hero/                 # Tbl 组：目录
    │   ├── HeroBase.tbl
    │   └── HeroSkill.tbl
    └── building.xlsx         # Xlsx 组：一个文件，sheet = 节点
```

- xlsx 组不再有 `<group>/<group>.xlsx` 包装目录。
- 同名冲突：`config/hero/` 与 `config/hero.xlsx` 同时存在 → 报错。
- 旧布局 `config/<group>/<group>.xlsx` 按 CLAUDE.md **不兼容**，读到直接报错并提示新路径。

### 4.2 schema 记录后端（manifest 阶段）

Phase 1 先按文件位置推导：`config/<group>/` = Tbl，`config/<group>.xlsx` = Xlsx。
进入 manifest 阶段后，再由 section 显式记录 storage：

```text
[hero/HeroBase] table
[building/Building] table xlsx
```

- 默认 `tbl`；`xlsx` 显式写。
- 组名仍是业务身份 `building`，文件路径由 `storage` 推导为 `config/building.xlsx`。
- 不采用 `[building.xlsx/Building]`：那会把文件名当组名，rename / 去重 / 校验都会变复杂。

### 4.3 模型与操作

- `Group` 增加明确的路径语义：Tbl 组的 `dir` 是组目录；Xlsx 组的 `dir` 是 `config` 根，`book_path() = dir/<name>.xlsx`。
- 新增/改名/粘贴/删除必须按 storage 分支：
  - Tbl：建/搬/删组目录；
  - Xlsx：建/改/删根级工作簿，**绝不能删除 `config` 根**。
- `load_groups_in` 同时扫描 `config/` 下的目录和根级 `.xlsx` 文件。
- `~$<group>.xlsx`、`.xlsx.tmp`、mtime+size 外部改动检测都落在 `config` 根。
- `Group::is_new` 的空白 xlsx 组保存时只建工作簿，不建同名目录。

### 4.4 影响面

- `project.rs`：组扫描 / xlsx load / reload。
- `ops.rs`：首次保存路径、rename、delete/emptied、group paste、clone、xlsx temp/lock。
- `tblschema.rs`：新建组按 storage 生成文件名；schema section 增加 storage。
- CLI / GUI 文档、shell 测试、Rust 单测中的 `config/xg/xg.xlsx` 全部改为 `config/xg.xlsx`。
- `.gitignore`：`~$*.xlsx` / `*.xlsx.tmp` 仍在任意层级生效，无需新增。

## 5. Phase 2 之后（不在本次）

- v4-lite：按维度 B 实现 schema-first 加载、v4 读写、`util`/skill 带 schema。
- manifest/template：按维度 C 拆分完整模板与运行时 manifest，并决定完整模板的文件名/版本头。
- 两者都要求先完成 Phase 1，否则 xlsx 组无法稳定表达“一个文件 = 一个组”。

## 6. 非目标

- 不做旧布局兼容或双路径读取。
- 不把 Excel 4 行表头当结构真相。
- 不在本次实现运行时 manifest 或 v4 文件。
