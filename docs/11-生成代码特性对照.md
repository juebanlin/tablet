# 生成代码特性对照

同一个 Project 可以同时导出多个语言的配置代码。本文档横向对照**各语言产物到底提供了哪些能力**，并记录**尚未对齐 / 尚未决策**的差异。

**范围：只描述导出器（`crates/core/src/export/`）的当前实现现状，不定义目标态。** 各语言「应该」长什么样由 §3 逐条决策；§5 是已经做完的那几轮对齐的记录。

读法：§2 看「现在各语言有什么」；§3 看「还剩哪些事，分别卡在哪」——分四类：**待决策**（要你先定口径）、**架构取舍**（单独议）、**工具链**（让人后知后觉的地方）、**有意为之的限制**（看着像 bug，别顺手改）。

## 1. 后端清单

一个 Project 最多同时产出 10 份代码，按「端」分两类：

| 后端 | 端 | 配置节 | 产物形态 |
|------|-----|--------|----------|
| Java | server | `[export.server.java]` | Tpl 类 + 一整套 runtime 模板 |
| Go | server | `[export.server.go]` | struct + 生成式 parse |
| C++ | server | `[export.server.cpp]` | struct + 内联 parse（header-only） |
| C# (.NET) | server | `[export.server.csharp_dotnet]` | class + 生成式 Parse |
| C# (Unity) | client | `[export.client.csharp_unity]` | 同上（仅 Loader 不同） |
| C# (Godot) | client | `[export.client.csharp_godot]` | 同上（仅 Loader 不同） |
| TypeScript (server) | server | `[export.server.typescript]` | interface + **数据字面量** |
| TypeScript (client) | client | `[export.client.typescript]` | 同上 |
| Lua | client | `[export.client.lua]` | 数据表字面量 |
| GDScript | client | `[export.client.gdscript]` | 数据字典字面量 |

C# 三个 runtime 的 **schema 类完全相同**，只在 `Loader.cs` 和字段可见性（server / client）上分三套。

字段可见性由 `.tbl` 的 `export` 标记决定，规则见 @02.9；枚举全量生成，不参与数据文件导出（@02.14）。

### 3.1 A 档：待决策（要先定口径才能动手）

**A1. 枚举 name↔值：值→名 已全语言补齐，只剩失败语义口径没统一**

| 能力 | Java | Go | C++ | C# | TS | Lua/GD |
|------|------|----|-----|----|-----|--------|
| id→实例 | ✅ `fromId` | 强转 | 强转 | 强转 | 强转 | 索引 |
| 名→值 | ✅ `valueOf`（JDK 自带） | ✅ `ParseXxx`（生成） | ✅ `ParseXxx`（生成） | ✅ `Enum.Parse`（BCL） | ✅ 索引 `X["NAME"]` | ✅ 表键 |
| 值→名 | ✅ `name()`（JDK 自带） | ✅ `String()`（生成） | ✅ `X_name(v)`（生成） | ✅ `v.ToString()`（BCL） | ✅ `XxxEnumNames[e]`（生成） | ✅ `names[e]`（生成） |
| 值→desc | 字段 | `Desc()` | `X_desc` | `GetDesc()` | `Desc[e]` | `desc[e]` |

（记号同 §2：`⚠️` 有但有限制 · `❌` 确实没有 · 无标记的格子里写的是实际做法。）

> **别只看「生成器有没有生成」**：Java / C# / TS / Lua 的 name↔值 大部分是**语言或标准库白送**的，不用生成器出码；只有 Go / C++ / 值→名方向的 TS·Lua 需要显式生成。

**补齐记录**：

| 后端 | 补了什么 |
|------|----------|
| C++ | `XEnum_name(v)`（值→名，未命中 `""`）+ `ParseXEnum(std::string_view)`（名→值，`std::optional`）。`enum class` 完全没有反射，不生成就真取不到 |
| Lua / GDScript | 枚举表里加了与 `desc` 并列的 `names = {[1]="RESOURCE"}` 反查表 |
| TS | 加了 `XxxEnumNames` 反查表。数值 enum 原生反向映射（`X[1] === "A"`）取出来是 `string`，且 Lua / GD 根本没有；统一出一张，七个后端写法一致 |

**场景澄清**（补这些的依据）：前后端通信只走枚举的 **int 值**；**name** 用于展示；**desc** 用于日志与代码审查。前端拿到服务端传来的 int 后要显示 name，正是 Lua / GD 之前缺的那一环。

**推迟：失败语义统一**。同样一句「按名字查枚举」，未命中行为四种写法：

| 语言 | 未命中时 |
|------|----------|
| Java | `valueOf` 抛 `IllegalArgumentException` |
| C# | `Enum.Parse` 抛异常，且走反射慢路径 |
| TS | 直接索引返回 `undefined` |
| Go / C++ | 分别返回 `(v, ok)` / `std::optional`，不抛 |

跨语言写同一套 GM / 配置工具时错误处理没法对齐。要动就得所有语言一起动，先定口径（比如统一提供「返回 ok / optional」的安全版）再开工，不适合单点改。

- **注意**：Java 的 `fromId` 不能删——`TplUtil.fromMap` 靠反射调它把原始 int 转成枚举实例；`valueOf` 是另一回事（按 name 查）。

**A2. 数据文件的 key 用 camelCase（已修，见 §5）**

原议题：数据文件的 key 走 `to_camel_case`（`stackMax`），与 `.tbl` 源名（`stack_max`）对不上，同一字段在链路上有三种拼法。
已按「当前没有外部系统消费这些数据文件」的判断改成用源名，明细见 §5。

**A3. CommonJS 模式的产物形态（已定论：直接废弃，见 §5）**

结论：**产物只出 ESM 一种形态，`module_kind` 已删除。**

原来的 CJS 分支连「模块」都不是——TS 判断一个文件是不是模块，只看源码里有没有顶层 `import` / `export`，而它一个都不写：

```ts
// 使用：const { Item } = require('./Item')
interface ItemTpl { ... }        // 声明了不导出，也没 .d.ts，消费者拿到 any
const Item: Record<number, ItemTpl> = { ... };
module.exports.Item = Item;      // 对 TS 而言这是「全局脚本」，不是模块
```

代价不只是「类型传不出去」：作为**全局脚本**，顶层 `const Item` 会进全局作用域，client / server 两侧各有一份 `Item.ts` 放进同一个 tsconfig 就会**重复声明报错**；`module` 也不是 TS 内置全局，得装 `@types/node`；常量的 `as const` 还会被丢掉。

而它换来的运行时收益是 **0**：Node 22.12+ 的 `require(esm)` 能直接 `require` ESM 产物（本机 Node 24 上两种形态实测都能跑）。CJS 消费方要 CJS，用自己 tsconfig 的 `module` 选项编译即可——原来的分支是在手写 `tsc` 会自动做的事，还写错了。

**兼容性：不留兼容层**。老 `project.toml` 里残留的 `module_kind` 会在加载时**直接报错**（两个 TS 导出段都开了 `deny_unknown_fields`），`--set …module_kind=…` 会得到一条「已废弃」警告。

### 3.2 B 档：架构取舍（需单独议，不适合顺手改）

**B1. `TblFieldType` 的双份真相**

Java 是唯一走「注解 + 反射」的后端：`TplHolder` → `TplUtil.fromMap` 反射读 `@TblFieldType` 拿类型串，交给 `Paradigm.of(tblType).parse()` 运行时解析。换来的是一份**与表无关的通用加载器**（reload / 批量回滚 / mismatchHandler 都是白送的）。

代价：`.tbl` 里的 `type:` 和注解 value 是**两处真相**，手改会漂移，且编译器不校验注解串写没写错。

三条可选路线：
1. Java 也生成静态 parse（注解可删）——最彻底，但丢掉通用加载器；
2. 保留反射加载器，把类型挪进生成的一份 schema 元数据——注解可删，加载器不变；
3. 保持现状，只把它当作文档化的设计取舍。

### 3.3 工具链：问题「后知后觉」都出在这里

**C1. `tablet-cli validate` 只打印位置，不打印消息（已修，见 §5）**

原文：输出只有 `[col] item/Item [18446744073709551615,6]`——既没有 `message`，`SCHEMA_ROW` 哨兵值还被直接打了出来。
已接上 `ProjectEngine::validate_errors()`，现在输出与 GUI 日志同款（含「表头第 4 行 G 列」定位）。明细见 §5。

**C2. `tablet-cli export` 退出码恒为 0**

@03.8.3 明确如此设计：「单格式失败仅 eprintln，不影响其它格式」。后果是：

- 流水线里 `export --all` 不会因为某个格式失败而 fail（撞名检测、C++ 的 rapidjson 未实现都会走这条路径）；
- 而且失败的格式**一个文件都不会更新**，所以是「静默产出陈旧产物」。

要卡流水线请用 `tablet-cli validate`（通过 → 0，任一错误 → 1）。`ExportSummary::has_failure()` 已经存在却没接到退出码上，看起来当初预留了。

### 3.4 有意为之的限制（看着像 bug，别顺手改）

- **C++ / C# 只支持 JSON**：两者的数据加载器没有 XML 路径。同时给 Java / Go 出 XML、又给 C++ / C# 出代码时，数据目录要额外导出 JSON（`export data --json`）。
- **枚举条目名不跟随语言惯例**：C# 枚举成员按惯例该是 PascalCase、Go 该是 MixedCaps，这里统一保持源里的 `UPPER_SNAKE`，为的是跨端日志与代码可 grep。理由与代价见 @01.8.1。
- **Java 只有服务端，Lua / GDScript 只有客户端**：没有反向的配置节，写进 `project.toml` 也不会生效。
- **TS / Lua / GDScript 是内联数据**：没有运行时加载器，因此也没有热更新 / GM 能力——数据改了必须重新导出代码，不能像 Java / Go 那样只换数据文件。
- **TS 的 `@枚举` 引用保留为 `number`，不映射成枚举类型**：TS 不允许把 `1` 赋给 `HeroTypeEnum` 类型（`Type 'number' is not assignable to type 'HeroTypeEnum'`），映射过去就得把 data 字面量改成 `HeroTypeEnum.WARRIOR` 或 `1 as HeroTypeEnum`，并且每个引用了枚举的表都要多一行 `import`——**破坏「每个 `.ts` 文件自包含」这个性质**。运行时值完全一样，收益只有 IDE 提示，代价不划算。所以这是有意保持现状。
- **Lua / GDScript 的枚举产物是普通 table / dict，不是语言级 enum 类型**：`HeroType.WARRIOR` 与 `1` 运行时就是同一个值，把引用字段「映射成枚举」在这里零收益。别试图给它套类型。
- **保留区间只保护区间内部，区间外一律覆盖**：`custom_regions` 是「手写业务代码怎么活过下一次导出」的答案，不是「生成文件可以随便改」。标记之外的任何手改（加字段、加 import、调顺序）下次导出都会没。想改结构就改 schema。相关边界见 @02.11。为什么 TS / Lua / GDScript 没有这个能力：它们的产物是数据字面量（`interface` + `const` 对象 / `return {…}` / `const X = {…}`），**根本没有类型体可以放方法**，给它们加标记只能是「往数据里再塞点数据」，没有意义。各后端的落点：Java 落在类体内、Go 落在文件末尾（方法必须是文件作用域的）、C++ 落在 struct 体内而枚举落在自由函数之后（`enum class` 装不了方法）、C# 落在类体内而枚举落在姊妹的 `{X}EnumExt` 静态类里。
- **TS / Lua / GDScript 不生成示例文件**：它们的 API 面只有一个对象字面量（`Item[2001]`），用法已写在每个文件头的 `使用：` 注释里。Java / Go / C++ / C# 需要 `Example.*` 是因为它们有加载器 API（`init` / `Get` / `All` / 常量单例）。别为凑齐对照表而生成。
- **Java 的 `@Getter` 只出注解，不带 jar**：`export.server.java.lombok` 默认开，生成器只往源码里写 `import lombok.Getter;` + `@Getter`，**既不打包也不附带 `lombok.jar`**——编译期依赖由消费方自己加。C# 不做对应选项：C# 的自动属性（`public int X { get; init; }`）本来就没有 getter 样板可省，而 C# 里"注解驱动生成代码"要靠 Roslyn 源生成器（attribute 本身改不了代码），没有 Lombok 的对应物，也不需要。两个代价都在消费侧：
  - **`boolean` 字段的 getter 从 `getXxx()` 变成 `isXxx()`**（Lombok 按 JavaBeans 惯例；源码依据 `HandlerUtil.toAccessorName`——`isBoolean` 为真时前缀取 `is`）。这与关掉开关时的产物**公开 API 不一致**，调用方要跟着改。想强制回 `get` 前缀得消费方自己加 `lombok.config`（`lombok.getter.noIsPrefix = true`），本项目不替消费方决定。选了这条路是因为 `isXxx()` 才是 Java 惯例，而 `getXxx()` 只是历史产物。
  - **JDK 23+ 编译时必须显式给 `-processorpath`**：JDK 23 起 javac 不再隐式运行 classpath 上的注解处理器，只写 `-cp lombok.jar` 的话 Lombok 会被**静默忽略**——exit 0、零警告，编出来的 class 里一个 getter 都没有（本机 JDK 25 实测；这与 §3.3 记的 C# Loader 事故同类）。用 `-processorpath` 而非 `-proc:full`，因为后者 JDK 21 才存在，CI 上的 JDK 17 认不出来。两条都有 e2e 盯着。

## 5. 附：已对齐记录

- **生成产物支持业务扩展保留区间**：`custom_regions`（四个后端段各自一个键，默认 `false`）。生成的类型里写一对 `// <TBL-CUSTOM-BEGIN>` / `// <TBL-CUSTOM-END>`，重新导出时把标记**之间**的内容原样搬过去。写入路径的改造是这次的关键：`sync_export_dir` 原本只收**已编码的字节**，而旧文件内容只有它拿得到，所以在各后端 `collect` 闭包里编码的旧做法行不通——改成收未编码的 `String` + `ExportOptions`，把「读旧文件 → 取区间 → 拼接 → 编码」收进一个函数。区间内容与磁盘逐字节相同时仍报「不变」，不会每次导出都重写文件。三个「手写代码可能丢」的情况会走 `ExportResult.warnings`（CLI 摘要、`--fmt json`、GUI 日志三处都显示）：新产物里没有标记（开关被关了）、标记写坏、标记重复/顺序颠倒。这条特性写错就是**静默吃掉用户代码**，所以核心拼接做成了纯函数并逐个钉边界（CRLF、缩进、空区间、重复标记），另加 e2e 把注入业务代码后的产物真编译一遍。**默认关**——不配这个键时产物与改动前逐字节一致。

- **Java 新增 `export.server.java.lombok`（默认开）**：表与常量类的逐字段 `public T getXxx()` 改成类上的 `@Getter`，`import lombok.Getter;` 只在开启时写。`ITpl` 声明的 `getId()` 仍显式保留（`TplHolder` 注册表在调它，且 Lombok 见同名方法会跳过，不会重复生成）。枚举类不参与——它的字段是 `public final`，`@Getter` 在那儿生成不出新东西。**这是破坏性变更**：`boolean` 字段的 getter 变为 `isXxx()`，详见 §3.4。顺带给 `JavaExport` 加上 `deny_unknown_fields`（与 TS 两个导出段一致），`[export.server.java]` 下拼错的键不再被静默吞掉；`util gen-test --lang java` 同步加了 `--lombok`，否则它生成的 `TestMain` 会去调已经不存在的 `getXxx()`。

- **CI 增加 codegen roundtrip 门禁**（`.github/workflows/ci.yml`）：`11_e2e` 现在会在每次 push / PR 上跑——把生成代码**编译并真的跑起来读数据**，覆盖 Java / Go / C# / C++ / Lua / TypeScript 六种产物。此前仓库只有发版 workflow，测试全靠手动跑，这正是 §3.3 那些「后知后觉」问题的温床。C# / C++ / Lua / TS 的 roundtrip 是本次新补的（Java / Go 原本就有）；缺工具链的用例 SKIP 而不是假装通过。
- **补上 TypeScript 的 roundtrip**：TS 占 10 个后端里的 2 个，此前是唯一**会生成真代码却没有 e2e** 的后端。新用例 `tests/11_e2e/test_typescript_roundtrip.sh` 走「`tsc --strict` 编译 → `node` 跑」，顺带把两件事钉成断言：产物必须是模块（顶层 `export`），且编译成 CommonJS 后 node 能直接 `require`——后者正是 `module_kind` 删掉之后 CJS 消费方的迁移路径。
- **修掉一条长期失效的测试**：`test_lua_roundtrip.sh` 断言的 `Item.price` / `GameConst.max_level` 都是 `export:服务器` 字段，客户端 Lua 产物里根本没有——`%d` 遇到 `nil` 直接让 lua 报错。它一直没暴露是因为本机 `command -v lua` 找不到已安装的 Lua（见下），这条长期处于 SKIP。改成断言客户端可见字段后 8/8 通过。
- **工具发现改用 `find_tool`**（`tests/helpers/common.sh`）：测试跑在 **Git Bash** 下，它和 cmd 的行为不同，有两个坑——PATH 里若有与可执行文件同名的**目录**会挡住同名 `.exe`（cmd 按 PATHEXT 搜且跳过目录，所以 cmd 下正常；LuaRocks 的 `C:\Program Files (x86)\Lua\5.1\lua` 正是把 `lua.exe` 挡住的元凶），以及装了但没进 PATH（Lua、npm 全局的 `tsc` 都是）。现在连 `<name>.exe` 一起找、支持额外搜索目录、并可用 `LUA_BIN` / `TSC` 等环境变量覆盖。同时 `run_all.sh` 与 `common.sh` 的默认构建从 release 改成 **dev profile**（@CLAUDE.md），`10_performance` 在非 release 构建下自动跳过。
- **修掉 C# Loader 的致命 bug：按文档用法一张表都加载不了**。`Loader.LoadAll` 读的是 `TblRegistry.Tables`，而那张表由各 `*Tpl` 的**静态构造器**填充；C# 的静态构造器是**惰性**的，不碰类型就不跑。于是 `Example.cs` 推荐的顺序（先 `LoadAll` 再 `HeroBaseTpl.Get`）此时注册表还是空的，`LoadAll` 静默什么都不做，`Get(id)` 全返回 `null`。修法：Loader 的 `LoadAll` 开头先 `EnsureTablesRegistered()`，用 `RuntimeHelpers.RunClassConstructor` 逐个强制跑一遍各 `*Tpl` 的静态构造器；三个 runtime 的模板都加了，并加测试断言占位符与 using 都在。**Go / C++ 没有这个问题**——`init()` 和文件级静态注册都在进程启动时执行，只有 C# 的静态构造器是惰性的。
- **`tablet-cli validate` 的输出带上了消息与表头定位**（原 C1）：此前只打 `[pid] group/node [row,col]`，没有任何消息，且表头层错误的 `row` 是 `SCHEMA_ROW` 哨兵值、直接打印成 `18446744073709551615`。现在 core 暴露 `ProjectEngine::validate_errors()`（结构化，带 `header_row` / `message`），CLI 复用 `format_validation_log`——与 GUI 日志同一套渲染，输出形如 `[验证] item/Item 表头第4行G列:[stage1] -> …`。`--fmt json` 也从元组数组变成带 `message` / `display` 的对象数组（@03.8.4）。
- **数据文件 / 查表 key 改用 `.tbl` 源名（原 A2）**：此前数据文件的 key 走 `to_camel_case`（`stackMax`），和源名（`stack_max`）对不上，于是同一字段在链路上有三种拼法（`.tbl` → JSON → 各后端 `row["stackMax"]` 配 `obj.StackMax`）。现在数据文件与四个 loader 的查表 key 统一用源名，全链路可 grep。**破坏性变更**——数据文件本身 + Java / Go / C++ / C# 的产物一起变了。Java 因为走反射、按字段名取不到源名，`@TblFieldType` 增加了 `name` 属性（只在源名 ≠ Java 字段名时生成，`id` 这类保持短形式）。TS 服务端不读 JSON（内联数据），不受影响。
- **废弃 `module_kind`，TypeScript 产物统一为 ESM（原 A3）**：删掉 `ModuleKind` 枚举、两个 TS 导出段的 `module_kind` 字段，以及 `typescript.rs` 里全部分支。原先「文件头注释按 `module_kind` 分支」的那次修复随之作废——分支本身没了。**不留兼容层**：两个 TS 导出段开了 `deny_unknown_fields`，老 `project.toml` 里残留的 `module_kind` 加载时直接报错；CLI 的 `--set …module_kind=…` 改为报「已废弃」而不是静默忽略。
- **枚举「值→名」全语言补齐 + 内联产物补遍历写法**：Lua / GDScript 的枚举表加了与 `desc` 并列的 `names` 反查表；TS 加了 `XxxEnumNames`。至此 §2 的「值→名」行只剩无记号或说明，不再有缺口。同时 TS / Lua / GD 的**表文件头**补了一行遍历写法（`Object.values(Item)` / `pairs(Item)` / `Item.values()`）——它们的 API 面只有一个对象字面量，遍历是唯一容易卡住的地方。
- **文档记号的语义定死**：`—` = 该能力在本产物形态下不适用（不是缺失），`❌` = 确实没有（后面写现状或替代做法）。据此把 `@枚举` 引用映射（Lua/GD）与「使用示例文件」（TS/Lua/GD）改判为 `—`，并把 TS 保留 `number` 的理由写进 §3.4。
- **字段命名对齐 + 撞名检测（验证层 + 导出层）**：TS 的字段名与常量名从源名 snake_case 改成 camelCase（`interface` 与 data 字面量同步转换），至此 7 个后端各自符合其语言惯例。同时新增转换后撞名检测——`.tbl` 允许 `stack_` / `stack__max` / `stage_1` 这类名字，转成 camelCase / PascalCase 后会与 `stack` / `stack_max` / `stage1` 塌成同一个键。现在**验证层**（`ValidationCode::NameCollision`）和**五个做转换后端的导出入口**都会拦，两处共用同一条文案。注意验证错误会阻止保存（@02），所以撞名现在和字面重名同级。规则见 @01.8.1。
- **C++ 生成代码现在能过 `-Werror`**：表和常量里没有任何复合类型字段（List / Set / Map / Tuple）时，`parse_Xxx(row, sep)` 的 `sep` 一次都用不到，之前会触发 `-Wunused-parameter`；现在这种情况显式生成 `(void)sep;` 吃掉。用 `g++ -std=c++17 -Wall -Wextra -Werror` 编译全部生成头已验证 0 warning。
- **desc 注入生成源码时统一转义**：`desc` 是原样透传的（`.tbl` 的 `desc:` 值不做反转义），所以 `"` `\` `*/` 都会原封不动进入生成文件。此前各语言把 desc 直接插进注释和字符串字面量——Java 的枚举 Javadoc 会被 `*/` 提前闭合、枚举构造参数的字符串字面量会被 `"` 截断，两者都会**直接编不过**。现在统一走 `comment_line()`（折叠换行）/ `comment_block()`（拆掉 `*/`）/ `escape_java_str()`，Go 与 C# 的字符串转义也补齐了换行/制表符（与 TS / Lua / GD 对齐）。
- **Java 枚举补 `getDesc()`**：与 `getId()` 配成一对，不再出现 id 双入口、desc 单入口的不对称。
- **@02.12 与实现对齐**：`IntPair.java` → 实际的 `Tuple2/3/4`；补上包内固定产出的运行时文件清单；`TplHolder` 的说明从「扫描 dataDir」改成实际的 `TblDataSource` 抽象 + 四个 `init` 重载 + 热更新/可插拔接口。@02.24 也从「Java / Go / Lua 三列」扩成全部 7 个后端（并补上「C++ / C# 只吃 JSON」这个此前没写进文档的约束）。
- **C++ 枚举补齐 name↔值**：新增 `X_name(v)`（值→名）与 `ParseX(name) -> std::optional<X>`（名→值），与既有 `X_desc(v)` 并列，语义对齐 Go 的 `String()` / `ParseXxx`。这是原 A1「缺得最多」的一项——`enum class` 没有反射，不生成就真的取不到。
- **枚举补 `getId()`**（Java）：与 Tpl 类的取值风格一致；枚举不实现 `ITpl`，所以接口层没有强制，此前一直缺。
- **字段注释全语言补齐**：此前只有 Java 导出字段说明。现在 C# 用 `/// <summary>`、TS 的 interface 字段用 `/** */`（常量值字面量跟行尾 `// desc`）、Go 与 C++ 跟字段行尾 `// desc`、Lua / GDScript 因导出物是纯数据字面量（没有字段声明位）改为文件头图例。
